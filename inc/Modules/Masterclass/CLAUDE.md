# Модуль Masterclass (`Inc\Modules\Masterclass`)

Публичные мастер-классы во внешних школах: временные аккаунты `student-N` / `Ученик#N` (учётка WP + физлицо + запись `student_records.is_trial = 1`
в служебной группе), флаеры с логином и паролем, вход в плеер без регистрации, заморозка по времени, воронка «вошёл → вернулся домой →
нажал «Связаться» → подал заявку → зачислен». Продукт — `.docs/masterclass-feature/SPEC.md`, имена и сигнатуры — `CONTRACTS.md`,
задачи по этапам — `tasks/`. Расходятся с кодом — правда в коде, а документы правятся в той же задаче.

## Правила модуля

- **Ядро о модуле не знает.** Связь — универсальные швы `fs_lms_*` (`CONTRACTS.md` §2), названные по смыслу ядра, и общие хуки WP. В `inc/`
  вне этого каталога, в `templates/` и `src/` нет слов «masterclass» и «мастер-класс»: единственное исключение — регистрация
  `MasterclassModule::class` в `Init::getServices()` (строки с этим классом). Стережёт `tests/Unit/Modules/Masterclass/ModuleBoundaryTest.php`.
- **Что регистрируется всегда, а что при включении.** `MasterclassModule::register()`: схема → настройки → целостность — ВСЕГДА (настройки, иначе
  модуль нечем включить; целостность и схема — потому что шов доступа, `deleted_user` и служебные группы читают таблицы и при выключенном
  модуле); страница, вход, плеер, зачисление, крон — только при `MasterclassConfig::isEnabled()`. Новая подписка, от которой зависит
  целостность данных, идёт в `MasterclassIntegrityController`; всё, что даёт возможности, — в «включённые» контроллеры. Подписка на метод,
  которого ещё нет, не регистрируется.
- **Заморозка выводится из времени** (`MasterclassDTO::isFrozen( $nowUtc )`: `now >= freeze_at`) и применяется только через шов Ш1
  (`LessonAccessPolicy::resolve()`). `frozen_at` — лишь отметка, что тик записал событие; продление сдвигает `freeze_at` и сбрасывает её.
  Новый путь доступа к занятию в ядре обязан идти через `LessonAccessPolicy::resolve()`.
- **Аккаунты не удаляются, а помечаются** (`masterclass_accounts.deleted_at`, `delete_reason`). Номер аккаунта — его `id`, он не повторяется;
  логин строит только `MasterclassAccountService::loginFor()`. Воронка считает и мягко удалённые (кроме `create_failed`: это номер без учётки).
- **Одноразовые отметки — условный `UPDATE … WHERE col IS NULL AND deleted_at IS NULL`** (`markFirstLogin / markHome / markContact / markFrozen /
  markDeleteRequested`); результат — `bool` («отметку поставил этот вызов»). Читать-потом-писать нельзя: два запроса одновременно поставят её дважды.
- **Заявку к аккаунту привязывает только `MasterclassConversionService`** по хуку, аккаунт берётся из сессии, а не из запроса.
- **Аккаунт с живой заявкой не удаляется, а отвязывается** (`DeleteStudentEvent` стёр бы заявку).
- **Удаление идёт порциями:** аккаунты (тик) → группа (`DeleteGroupEvent`); любой чужой путь удаления группы проходит через Ш3.
- **Время.** Колонки `masterclasses` / `masterclass_accounts` / `masterclass_log` — UTC (переводит только `ExamTime`), колонки `group_lessons` — местное.
  `created_at` / `updated_at` пишутся явно (`DEFAULT CURRENT_TIMESTAMP` берёт пояс БД, не UTC).
- **`groups.id` — `smallint unsigned`.** `masterclasses.group_id` того же типа: больший id БД молча обрежет, и ссылка поедет на чужую группу.
  В тестах на `wp_db` брать `group_id` ≤ 65 535.
- **Журнал — после успешной операции, вне блокировок, сбой записи гасится.** Пароли и ПД не пишутся (`MasterclassLogWriter` дополнительно
  вырезает из `context` ключи, похожие на `pass|pwd|secret|token|nonce`). Подпись объекта — «Ученик#N», запрос в БД ради неё не нужен.
- **Ошибка БД в репозитории — исключение**, а не «строки нет» (`AbstractExamRepository`). Подписчик шва ядра, который читает таблицу модуля
  (Ш4), сам гасит сбой и возвращает список как пришёл: сбой модуля не должен ронять зачисление и выгрузку ядра.
- **Данные вкладки настроек не называть `$config`.** `templates/admin/settings.php` держит под этим именем массив настроек плагина, а
  `extract( $tab['data'], EXTR_SKIP )` существующую переменную не перезапишет: шаблон получит чужое значение и упадёт на живой странице
  (так упала вкладка 2026-10-28, юнит-тест этого не видел). Ключ — `masterclass_config`; рендер-тест повторяет механизм страницы настроек.
- **Аккаунт собирается по шагам и откатывается вручную.** `wp_insert_user()` транзакцией не откатывается, поэтому `createChunk()` создаёт физлицо → учётку → запись → привязку, а при сбое сначала
  помечает строку `create_failed`, затем снимает созданное событием `DeleteStudentEvent` (сбой отката не прерывает порцию). Группа + занятие + строка мастер-класса, наоборот, создаются в одной
  транзакции (`MasterclassService::create()`), журнал — после `COMMIT`.
- **Правка мастер-класса, не двигавшая окно, сроки и отметки тика не трогает** (иначе школа или преподаватель затёрли бы «Продление»). Предмет мастер-класса не меняется; урок — только пока по занятию нет данных учеников.
- **Любое место ядра, где ученики перечисляются, выгружаются или переносятся, обходит служебные группы через `ServiceGroupResolver`** (`isService()`, `onlyServiceRecords()`), а новый такой путь
  обязан пройти аудит: пакет переноса предмета несёт пароли открытым текстом, поиск «Ученик» без фильтра возвращает сотни временных аккаунтов. Решения по найденным местам — `tasks/stage-02.md` п. 2.7.
- **Тик удаляет порциями с общим бюджетом** (`ACCOUNTS_PER_TICK = 60` на «неиспользованные» + «просроченные»), каждый шаг выбирает только необработанное и идемпотентен. Выборки аккаунтов к чистке (`nextPurgeable`) берут только живых с записью в группе: отвязанные не выбираются, пропущенные (аккаунт с заявкой при истёкшем сроке) обходятся курсором. Группа сносится, когда `countAttached() === 0`. Новый шаг тика не должен выбирать то, что сам не помечает обработанным: иначе он будет сидеть на одних и тех же строках и съедать бюджет.
- **Крон модуля — только при включении, снимается при выключении** (`onToggle( false )`). Тело тика — под `ExamTickLock`; проверка из крона — `docker compose run --rm wpcli wp cron event run fs_lms_masterclass_tick` (первый тик на dev-стеке срабатывает и сам из WP-Cron).
- **JS-страница добирает аккаунты порциями по набранному числу** (`addAccounts()` в `assets/admin.js`): порция может создать меньше, чем просили (занятый логин, сбой); после трёх пустых порций подряд цикл
  прекращается. Прогресс — «создано X из Y»; промежуточные сообщения в одном такте браузер склеивает, это норма.
- **Заглушка `add_query_arg` в юнит-тестах принимает только массив аргументов** — в шаблонах `add_query_arg( array( 'paged' => 2 ), $url )` (тест обнаружил форму `add_query_arg( 'paged', 2, $url )`).
- **Строка PHP `"…$name»"`**: символ `»` (как и любой не-ASCII) считается частью имени переменной. В тестах с русским текстом — `{$name}`.
- Остальное — как во всём проекте: слои (Controllers — хуки; Callbacks — AJAX; Services — логика; Repositories — БД), AJAX-экшены — константы
  контроллера модуля (не `AjaxHook`), `Nonce::Config` + `Capability::ManageLmsPlatform` для админки, `Nonce::LearnerActivity` для плеера,
  ввод через `Sanitizer`, HTML — в `templates/` модуля, стили — токены, инлайновых `style=` и `<svg>` нет.
