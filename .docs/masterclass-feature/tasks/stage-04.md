# Этап 4. Тик и удаление

Зависимости: этапы 1–3 (аккаунты, заморозка, журнал), этап 0 (Ш3).
Результат: каждые 15 минут модуль пишет в журнал заморозку, удаляет неиспользованные и просроченные аккаунты порциями, сносит группу, когда удалять некого,
подчищает зависшие строки и старый журнал; удаление группы любым путём не оставляет учёток `student-N`; «Удалить» на странице работает (отложенно).

Перед началом прочитать `README.md`, `../SPEC.md` §2 (решения 5, 7, 16, 18, 19), §4 («Тик»), §8, §9, `../CONTRACTS.md` §8 (`MasterclassLifecycleService`), §9
(`MasterclassCronController`, `MasterclassIntegrityController`).

**Порядок:** 4.1 → 4.2 → 4.3 → 4.4 → 4.5.

## Статус

**Готов и проверен 2026-10-29** (код закоммичен в ветке, не запушен). Итог:

- `MasterclassLifecycleService` (тик, Ш3 `onGroupDeleting`, `onUserDeleted`), `MasterclassCronController`; подписки `fs_lms_group_deleting` и `deleted_user` — в `MasterclassIntegrityController` (всегда), снятие хука при выключении — в `MasterclassSettingsController::onToggle()`; `MasterclassModule` получил `$cron`. «Удалить» на странице (4.3) работало с этапа 2 (`ajaxDelete()` → `requestDelete()`), здесь проверен хвост — вычистка тиком.
- **Отличие от контракта:** `MasterclassAccountRepository::nextPurgeable( $id, $limit, $afterId = 0 )` теперь берёт только аккаунты с записью в группе (`student_record_id IS NOT NULL`) и принимает курсор; новый `countAttached()`. Без этого отвязанный аккаунт с заявкой выбирался бы каждый тик вечно, а пропущенные (срок вышел без «Удалить») занимали бы окно выборки. Группа сносится, когда `countAttached() === 0` — отвязанные не держат её (контракт говорил «countLive … или все отвязаны»).
- Правила: бюджет 60 общий на шаги «неиспользованные» и «просроченные»; аккаунт с живой заявкой — отвязка при «Удалить» и при удалении группы, при простом сроке остаётся (группа живёт); `finish()` ставит `purged_at` и пишет `MasterclassPurged` один раз (Ш3 мог успеть раньше).
- Проверки: PHPUnit 4621 зелёные (тесты сервиса, крон-контроллера, настроек, целостности, репозитория); DI вкл./выкл.; на стенде `wp_db` (200 аккаунтов, WP-CLI `wp cron event run fs_lms_masterclass_tick`, скрипт в scratchpad, данные удалены).
- **4.4 на стенде:** два тика одновременно — один отработал (0,31 с), второй упёрся в замок (0,002 с), удалено ровно 60; бюджет: 60 + 60 + 60 + 15 (тики 1–4), пятый тик ничего не делает, `unused_purged_at` ставится на 4-м; `frozen` в журнале — одна запись; после `purge_at` оставшиеся 5 удалены с причиной `expired`, группа и занятие снесены, `purged_at` стоит, остатков (учётки, физлица, записи) нет. Из WP-Cron реально удаляет (предусловие §11 п.1): первый тик вообще сработал сам из WP-Cron. «Удалить» при аккаунте с заявкой: отвязан (учётка, физлицо и заявка остались, записи в группе нет), группа снесена, остальные удалены с причиной `requested`. Удаление группы напрямую (`DeleteGroupEvent`, путь страницы «Группы»): аккаунты удалены с причиной `group_deleted`, держатель заявки отвязан, мастер-класс помечен вычищенным. `wp_delete_user()` помечает аккаунт `user_deleted` и пишет в журнал. Данные по занятию уходят вместе с группой (занятия снесены).
- **4.5 шум журналов ядра:** удаление 60 аккаунтов + группы дало **+61 строка** в `entity_audit_log` (по одной на аккаунт и на группу), остальные таблицы журналов без изменений; создание из CLI строк не добавило (в проде под пользователем-офисом возможны записи `UserCreated`, замер не из админки).
- Не проверено: PHPStan (нет в контейнере); снос предмета целиком (тот же `DeleteGroupEvent`, отдельно не гонял); два тика в одном процессе по ходу создания «Докинуть» (удаление запрещает добавление — юнит-тест сервиса этапа 2).
- **Для этапа 5:** зачисленный аккаунт (`Enrolled`) не выбирается тиком, но его временная запись, если она осталась в группе мастер-класса, снесётся вместе с группой (групповая чистка собирает `is_trial = 0`, временные — нет, но запись зачисленного уже не `is_trial`); `markEnrolled()` обязан убедиться, что у ученика есть настоящая запись в другой группе, а запись в группе мастер-класса снята. Конструктор `MasterclassConversionService` сейчас `( MasterclassAccountRepository, MasterclassLogWriter, ClockInterface )` — этап 5 его расширяет.

  `onUserDeleted()` (`deleted_user`): `markDeletedByUserId( UserDeleted )`; журнал только если поставилось.
- [x] Тесты: бюджет, идемпотентность каждого шага (повторный тик ничего не делает), отвязка при `delete_requested_at`, группа не удаляется при живом аккаунте с заявкой,
