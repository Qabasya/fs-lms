# Мастер-классы: спецификация

Статус: черновик, ред. 3 (2026-10-28) — фича оформлена **модулем** `Inc\Modules\Masterclass`; ред. 3 сверена с `master` 1.1.85 (§16).
Контракты классов — `CONTRACTS.md` (правда о именах и сигнатурах; расходятся с кодом — правда в коде, этот файл и
`CONTRACTS.md` правятся в той же задаче).

Всё, что названо без пометки «(новое)», проверено по коду. Правила, которым подчиняется реализация: корневой `CLAUDE.md`
(слои, DI, Sanitizer/Authorizer, «Правила качества», «Сначала существующее», «Модули») и `.docs/basic_doc.md`
(§5 раскладка, §7 AJAX, §13 админ-страницы, §14 модалки, §26 опциональные модули).

## 1. Зачем

Мы приходим в школу, раздаём флаеры с логином и паролем, дети проходят один урок в плеере прямо на занятии, дома заходят теми
же данными и допроходят. Дома их встречает баннер «запишитесь на занятия». Цель — воронка: школа → мастер-класс → вход дома →
заявка → зачисление.

## 2. Решения

1. **Модуль, а не слой ядра** (`basic_doc.md` §26: «новая крупная фича — по умолчанию лист»). Мастер-классы — маркетинговая
   надстройка: без них учебная часть работает. Ядро **не импортирует** классы модуля, не знает его таблиц, опций, AJAX-экшенов
   и прав. Связь — только через WP-хуки: существующие (`fs_lms_application_created`, `fs_lms_student_enrolled`,
   `fs_lms_settings_tabs`, `fs_lms_dashboard_modules`, `wp_login`, `deleted_user`, `template_redirect`, `login_redirect`) и
   **семь новых универсальных швов ядра** (§10). Швы названы по смыслу ядра («служебные группы», «блокировка плеера»), а не по
   мастер-классам — ими сможет пользоваться любой следующий модуль.
2. **Мастер-класс — не новый тип проведения.** Это открытая группа (`AccessMode::Open`) с одним занятием (`group_lessons`),
   привязанным к уроку из банка. Курса-обёртки нет (`groups.course_id = NULL`; плеер и КТП это уже держат:
   `CourseNavService::shell()` берёт название группы, `ProgramCompositionService::getProgram()` читает строки занятий).
3. **Занятие стоит в расписании:** `scheduled_at` = начало, `ends_at` = конец (местное время, как у всех `group_lessons`),
   `visibility = open`, `opened_at = NULL`. Следствия, проверенные по коду: до начала урок закрыт штатным экраном «Урок ещё не
   доступен» (`LessonGateResolver::dateReached()`), уведомление «урок открыт» не рассылается (`listRecentlyOpened()` берёт
   `open` только по `opened_at`), занятие видно преподавателю в расписании, «журнал не заполнен» и «нет записи» открытые группы
   пропускают (`NotificationCronService::journalNotFilled()/recordingMissing()`, `AdminAlertService::activeGroups()`).
4. **Единица — школа + дата (один визит).** 3–4 класса в тот же день — один мастер-класс с общим запасом аккаунтов; любой
   ребёнок берёт любой флаер. Другой визит — другой мастер-класс.
5. **Временные аккаунты.** Логин `student-N`, имя `Ученик#N` (фамилия физлица и `display_name`), пароль — 8 символов без
   путаницы `0/O`, `1/l/I`. `N` — `id` строки аккаунта. Строки аккаунтов **не удаляются никогда** (мягкое удаление,
   `deleted_at`), поэтому номер не повторяется и после перезапуска СУБД, а воронка переживает чистку. `#` в логине невозможен:
   `wp_insert_user()` и `UserManager::changeLogin()` зовут `sanitize_user( …, true )`.
6. **Запись ученика — временная** (`student_records.is_trial = 1`, `parent_person_id = 0`): такие записи уже исключены из
   AD-провижна, отчисления, печати договоров и аудитории экзаменов, а `EnrollmentTransaction` удаляет временную запись при
   зачислении.
7. **Сроки от конца мастер-класса.** Заморозка — через `freeze_days` (14); аккаунты без входа удаляются через
   `unused_purge_days` (7); остальные — через `frozen_purge_days` (30) после заморозки. Сроки фиксируются в мастер-классе при
   создании; смена настроек идущие не сдвигает. «Продлить» сдвигает сроки всего мастер-класса.
8. **Заморозка выводится из времени** (`now ≥ freeze_at`), а не из флага: доступ закрывается ровно в срок через шов
   `fs_lms_lesson_access` (§10, Ш1). Тик нужен только для журнала и удаления. Вид — штатный экран блокировки плеера (размытый
   скелет + окно), текст окна подставляет модуль через шов Ш2.
9. **Где ребёнок вошёл.** До начала — «до начала» (вход не считается первым). Внутри окна — «на месте». После окна или
   повторный вход позже `home_timeout` (60 мин) после первого — «дома». «Дома» отмечается **и при открытии плеера после
   окончания**: при живой сессии (ребёнок входил со своего телефона) `wp_login` дома не срабатывает.
10. **Выход из аккаунта.** У временного ученика в шапке плеера кнопка «Выйти» (`wp_logout_url()` → `/sign-in/`): школьные
    компьютеры за день делят 3–4 класса, а кабинета, где есть выход, у ребёнка нет.
11. **Кабинета у временного ученика нет:** `/profile/` и `/sign-in/` ведут его в плеер его мастер-класса (модуль вешает свой
    `template_redirect` раньше `ProfileController`, приоритет 5), после входа — туда же (`login_redirect`). Кнопки «Назад» в
    плеере у него нет (шов Ш2).
12. **Превращение в настоящего ученика.** Ребёнок открывает `/apply/` из баннера (залогиненным); направление и школа
    предзаполнены (шов Ш5). Сервер по хуку `fs_lms_application_created` привязывает заявку к физлицу аккаунта, переносит
    введённые логин и пароль на учётку (готовый `TrialAccessService::syncCredentials()`) и ставит «подал заявку». Аккаунт —
    из сессии, не из параметра адреса. **Смена логина и пароля сразу завершает сессию** (кука входа подписана логином и
    фрагментом хеша пароля) — экран успеха заявки говорит «теперь входите с новыми логином и паролем». При зачислении
    `EnrollmentService` переиспользует учётку и физлицо, `EnrollmentTransaction` дописывает в физлицо данные из заявки и удаляет
    временную запись, модуль по `fs_lms_student_enrolled` ставит «зачислен» и **переписывает имя учётки WP** (`display_name`,
    `first_name`, `last_name`) из физлица — иначе шапка кабинета (`ProfileViewResolver`) так и покажет «Ученик#N».
13. **Окно «Связаться»:** телефон (существующий `PluginConfig::centerContactsFallback()['phone']`), ссылка на мессенджер
    (настройка модуля), «Заполнить заявку» → `/apply/`. Короткая форма «Перезвоните мне» — не в первой версии.
14. **Преподаватель** показывает урок штатным путём (кабинет → группа → КТП → урок). Проверка работ не нужна, поэтому **урок
    обязан быть полностью автопроверяемым** — то же правило, что у открытых курсов (`OpenCourseValidator`, проверка выносится
    в метод по одному уроку).
15. **Служебная группа.** Группа мастер-класса не должна попадать туда, где сотрудник выбирает группу для настоящего ученика:
    модуль объявляет её через шов `fs_lms_service_group_ids` (Ш4), ядро исключает такие группы из выбора группы при
    зачислении, из «Добавить в открытую группу» и из выгрузки учеников.
16. **Удаление группы любым путём** (страница «Группы», снос предмета, сам модуль) сначала даёт модулю убрать аккаунты: шов
    `fs_lms_group_deleting` (Ш3). Без него `GroupDeletionHandler` временных учеников не удалит: «сироты» собираются только с
    `is_trial = 0` (`StudentRecordRepository::deleteAllByGroupAndCollect()`), учётки `student-N` остались бы навсегда.
17. **Пачки — порциями.** Один запрос создаёт не больше 25 аккаунтов (хеш пароля ~50 мс + 5–6 вставок + записи аудита на
    аккаунт): создание пачки на 60–500 и «Докинуть» гоняет страница циклом запросов с прогрессом.
18. **Удаление мастер-класса — отложенное:** «Удалить» помечает мастер-класс к удалению, тик вычищает аккаунты порциями и в
    конце удаляет группу. Аккаунты с живой заявкой при явном удалении **отвязываются** (снимается только временная запись,
    учётка и физлицо остаются за заявкой, `trial_owner = 1`), а не удаляются: `DeleteStudentEvent` стёр бы заявку
    (`StudentDeletionHandler` → `applications->hardDeleteByStudentPersonId()`).
19. **Журнал «Мастер-классы»** — своя таблица модуля и вкладка «Журнал» на странице модуля (core-энум `LogChannel` модуль
    расширять не может). Записи старше `log_retention_days` (365) тик удаляет: в контексте есть IP.
20. **Где в админке.** «FS LMS → Мастер-классы» — подстраница под `Menu::Main`, регистрирует модуль через `MenuManager`.
    Право — существующее `Capability::ManageLmsPlatform` (у него ровно офис и администратор): своё право модуля не провести
    через `Authorizer` (он принимает core-энум), а матрицу ролей ядро модулям не открывает. Флаеры (выгрузка паролей) — тем же
    правом, пишутся в журнал.
21. **Флаеры** — отдельный печатный HTML-документ (`@media print`, 4 на A4), отдаёт его `admin-post.php`-обработчик модуля и
    завершает запрос (страница меню выводится после шапки админки — «без обвязки» там не получить). `PrintCenterService` не
    подходит: он собирает DOCX/PDF по записи зачисления с родителем.
22. **Вход в школе при заблокированной капче.** Если скрипт Яндекса не дошёл до браузера, ядро пропускает без капчи не больше
    30 входов в час на IP (`RateLimitService::LIMIT_CAPTCHA_FALLBACK_LOGIN`), а вся школа — за одним IP. Модуль через шов
    `fs_lms_captcha_fallback_unlimited` (Ш6) снимает этот лимит **только** для логинов `student-N` мастер-класса, окно
    которого идёт сейчас (с запасом 30 минут до начала). Перебор паролей по-прежнему держит `LoginGuardService`, но блокировка теперь
    ступенчатая (с 1.1.85): 3 неудачи за 5 минут на пару IP + пользователь закрывают вход на 15 минут, следующие 3 после неё —
    на час, затем на сутки (ступень помнится сутки). Пара считается по логину, поэтому дети с разными `student-N` за одним IP
    друг другу не мешают; ребёнка, трижды ошибившегося, выручает запасной флаер, а весь класс сразу — решение 23.
23. **Снять блокировки класса.** На странице мастер-класса — действие «Снять блокировки»: для каждого живого аккаунта
    `LoginGuardService::unlockUser()` (отметка сброса по пользователю действует со всех адресов и возвращает первую ступень).
    Нужно, когда класс за одним IP в 11:00 разом ошибается из-за раскладки или Caps Lock и ждать 15 минут (а повтором — час)
    на 45-минутном занятии нельзя. Право — то же `ManageLmsPlatform`; в журнал модуля пишется число снятых блокировок.
24. **Аккаунты видны на странице модуля, а не во вкладке «Ученики»; хранятся в записях ядра.** Временный ученик — настоящие `wp_users`,
    `persons` и `student_records` (`is_trial = 1`) в служебной группе. Отдельная таблица вместо них невозможна: прогресс, сдачи, попытки,
    посещаемость и проверки заданий лежат в семи таблицах ядра по `student_person_id`, доступ к уроку `LessonAccessPolicy` читает из
    `student_records`, плеер находит ученика по `persons`, а удаление (`StudentDeletionHandler`) требует `is_student`; своя модель обучения
    значила бы дублировать плеер или вскрывать ядро. Таблица модуля `masterclass_accounts` — учёт (состояние, вход, «дома», «связался»,
    заявка, сроки), и на ней строится воронка. Плата за этот выбор — каждое место ядра, где ученики перечисляются, надо осмотреть:
    этап 0 закрыл четыре (зачисление, добавление в группу, выгрузка, вкладка «Ученики»), остальные — аудит этапа 2 (`tasks/stage-02.md`
    п. 2.7) с таблицей решений. На странице модуля у каждого мастер-класса — свой **список аккаунтов**: номер, логин `student-N`, состояние,
    первый вход, «дома», «связался», заявка, для удалённых — причина; пароли в списке не показываются (они только на флаерах, с записью в
    журнал); 50 на страницу, удалённые — по галочке. Так офису и преподавателю не нужно искать детей в общих списках.

## 4. Потоки

**Создание** (`MasterclassService::create`): проверка входа → текущий период → в транзакции группа (`access_mode = open`,
`teacher_id`), занятие (расписание по решению 3, снимок работ урока), строка `masterclasses` → журнал. Аккаунты — отдельными
запросами `AddAccounts` по ≤ 25 (страница крутит цикл до нужного размера пачки).

**Создание аккаунта** (`MasterclassAccountService::createChunk`): на каждый — (1) строка без `user_id` → `N`; (2) физлицо
`Ученик#N`; (3) учётка `student-N`; (4) временная запись в группе; (5) привязка. Сбой шагов 2–5 — откат созданного для этого
аккаунта, строка помечается удалённой (`reason = create_failed`), порция продолжается. Логин уже занят — номер пропускается тем же
путём.

**Вход** (`wp_login`): отметка первого входа, «до начала / на месте / дома», журнал. Пропускаются удалённые и зачисленные.

**Открытие плеера:** `template_redirect` модуля (маршрут плеера) отмечает «дома» после окна; швы Ш2 рисуют баннер, «Связаться»,
«Выйти», убирают «Назад», подставляют окно заморозки.

**Заявка:** решение 12.

**Тик** (каждые 15 минут, свой хук модуля): журнал заморозки → удаление неиспользованных → удаление просроченных и помеченных
к удалению → удаление группы, когда удалять больше некого → подчистка зависших строк → срок хранения журнала. Лимит — в
аккаунтах за тик (60), каждый шаг идемпотентен и не выбирает уже обработанное (признаки `unused_purged_at`, `purged_at`).

## 5. Права

`Capability::ManageLmsPlatform` на страницу, все действия, настройки и флаеры. `fs_lms_caps_version` не меняется.

## 6. Настройки (вкладка «FS LMS → Настройки → Мастер-классы», только при включённом модуле)

Опция модуля `fs_lms_masterclass` (`MasterclassConfig extends ModuleConfig`), константа-тумблер `FS_LMS_MASTERCLASS`. В core
`OptionName` и `PluginConfigRepository` ничего не добавляется. Сохраняет офис (`ManageLmsPlatform`).

| Ключ | Тип | По умолчанию | Границы |
|---|---|---|---|
| `enabled` | bool | `false` | — |
| `start_time` / `end_time` | `HH:MM` | `09:00` / `14:00` | валидное время, конец позже начала |
| `batch_size` | int | 60 | 1–500 |
| `home_timeout_minutes` | int | 60 | 5–720 |
| `freeze_days` | int | 14 | 1–60 |
| `unused_purge_days` | int | 7 | 1–60 |
| `frozen_purge_days` | int | 30 | 1–365 |
| `log_retention_days` | int | 365 | 30–1095 |
| `messenger_url` | url | пусто | `esc_url_raw` |
| `banner_text` | текст | «Свяжитесь с администратором, чтобы записаться на занятия» | ≤ 300 |

## 7. Журнал «Мастер-классы» и воронка

Таблица модуля `fs_lms_masterclass_log`, действия — `MasterclassLogAction` (значение кейса не менять). Запись — после успешной
операции, вне блокировок; сбой записи действие не ломает. Не пишем: пароли, персональные данные. IP — только в контексте входа.

Воронка считается по колонкам аккаунтов (строки не удаляются — решение 5): создано → входили → вернулись домой → нажали
«Связаться» → подали заявку → зачислены. Журнал — для разбора «кто и когда».

## 8. Выключение модуля

Выключенный модуль не регистрирует рантайм (меню, крон, редиректы, плеер, привязку заявок), но **всегда** регистрирует:
настройки и карточку (иначе не включить), шов заморозки Ш1 и `deleted_user` (иначе выключение открыло бы замороженные уроки и
сломало учёт удалённых), а также служебные группы Ш4 (иначе группа вернулась бы в списки зачисления) и удаление группы Ш3 (иначе учётки
`student-N` остались бы сиротами). Таблицы и аккаунты выключение не трогает — перед выключением мастер-классы удаляют на странице модуля.
Крон-хук снимается в обработчике `fs_lms_module_toggle_masterclass` (как `AdSyncCronController::unschedule()`).

## 9. Риски и известные поведения

- **Заявка истекла или в корзине** → `TrialAccessService::revoke()` удаляет учётку и физлицо раньше срока (`trial_owner = 1`).
  Модуль узнаёт об этом по `deleted_user` и помечает аккаунт удалённым (`reason = user_deleted`). Требует исправленного
  `UserManager::delete()` (§11, п. 1) — иначе из крона удаление падает.
- **Временный доступ в настоящую группу для подавшего заявку** (`TrialAccessService::grant()`) в первой версии недоступен:
  `findTrialByStudent()` видит запись мастер-класса и отвечает «уже выдан». Кнопки «Продлить» / «Снять доступ» у такой
  заявки действуют на запись мастер-класса («Снять» удалит аккаунт — он принадлежит заявке). Офис зачисляет такого ребёнка
  после анкеты родителя.
- **Перелогин в классе позже часа** считается «дома»: баннер увидит ребёнок в классе. IP пишется в контекст для разбора.
- **Шум журналов ядра:** провизия пишет `UserCreated`, удаление ученика — `EntityHardDeleted` + `UserDeleted` в «Действия»
  (~3 строки на аккаунт). В первой версии принимается.
- **Простой пароль + предсказуемый логин:** перебор держит ступенчатая блокировка `LoginGuardService` (15 минут → час → сутки по
  паре IP + логин); аккаунт без ПД открывает один урок.
- **Блокировка в классе:** ребёнок, ошибившийся трижды за 5 минут, теряет 15 минут занятия — запасной флаер выдаёт
  преподаватель, снять блокировки всем — офис (решение 23). Блокировка не обходится капчей и шов Ш6 её не трогает.

## 10. Изменения ядра (универсальные швы)

Ядро не знает слова «мастер-класс». Каждый шов — один `apply_filters`/`do_action` с докблоком и тестом ядра «без подписчиков
поведение прежнее».

| # | Шов | Где | Зачем модулю |
|---|---|---|---|
| Ш1 | фильтр `fs_lms_lesson_access` | `LessonAccessPolicy::resolve()` | заморозка; ядро принимает только понижение уровня |
| Ш2 | фильтры `fs_lms_player_back_url`, `fs_lms_player_lock_html`; экшены `fs_lms_player_header_actions`, `fs_lms_player_before_content`, `fs_lms_player_footer` | `LessonPlayerController` + `player.php`, только вид ученика | баннер, «Связаться», «Выйти», окно заморозки, без «Назад» |
| Ш3 | экшен `fs_lms_group_deleting` | `GroupDeletionHandler::handle()`, до транзакции | убрать аккаунты до сноса группы |
| Ш4 | фильтр `fs_lms_service_group_ids` | выбор группы при зачислении, `OpenGroupEnrollmentService::enrollableGroup()` (общая проверка `enrollMany()` и `planFromSubject()`), `StudentsExportProvider` | группа мастер-класса — служебная |
| Ш5 | фильтр `fs_lms_apply_prefill` | `ApplyPageController::renderApplyForm()` | предзаполнить направление и школу |
| Ш6 | фильтр `fs_lms_captcha_fallback_unlimited` | `CaptchaService::check()` | вход класса за одним IP без капчи |
| Ш7 | правило данных без хука | `StudentRecordRepository::findActiveTrials()` | плитка «ждём анкету родителя» — только ученикам с заявкой (так устроен `TrialAccessService`); записи мастер-класса без заявки её не получают |

Плюс общий компонент плеера `.s-banner` (плашка над уроком) в `src/scss/player/components/_shell.scss` — модуль выдаёт
разметку штатных классов и своих стилей в плеер не грузит.
