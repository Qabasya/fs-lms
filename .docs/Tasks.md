# Публичные экзамены: этапы реализации

Источник требований — `.docs/public-exam-feature/SPEC.md` (приоритет), решения — `DECISIONS.md`. Ветка `public-exams`. Слои кода следуют `CLAUDE.md`. Мокап — иллюстрация, не исходник. **Перед каждым новым классом, сервисом или UI-элементом — сначала найти готовое в проекте** (сервисы, Callbacks, JS, SCSS, шаблоны) и использовать его; если оно почти подходит, дорабатывать существующее, а не дублировать 70–80% кода. Новое допускается, только когда аналога нет (причина — в описании задачи).

Каждый этап самостоятельный: у него есть результат, который можно проверить отдельно, не дожидаясь следующих. Этап считается закрытым, только когда пройдены его проверки (PHPUnit, `npm run ci`, ручная/e2e-проверка), а не когда нарисован UI. Этапы идут по порядку; зависимости указаны.

**Детализация для исполнителя** — `.docs/public-exam-feature/tasks/`: общий `README.md` (правила, рецепты, контракт имён) и по файлу на этап. В каждом пункте — что меняется, в каких файлах, зачем, что проверить до начала, какими тестами покрывается и когда пункт считается закрытым. Здесь, в `Tasks.md`, остаётся обзор и отметки выполнения.

## Вехи (что можно выпускать отдельно)

| Веха | Этапы | Что получают пользователи |
|---|---|---|
| **M1. Запись** | 0–5 | Преподаватель назначает экзамен, ученики записываются, родитель смотрит. Экзамен ещё не сдаётся |
| **M2. Сдача и результаты** | 6–10 | Сдача на существующей станции, неявка, проведение, проверка и массовое утверждение, «Результаты», уведомления, статистика |
| **M3a. Гость: заявка и оплата** | 11a | Гость по ссылке школы выбирает сеанс, держит место, платит в WooCommerce и получает подтверждённую запись; администраторы платформы разбирают проблемные оплаты. Решения по форме и броне приняты 2026-10-02, блокера нет. Идёт параллельно этапам 5–8 (нужны только 2–4) |
| **M3b. Гость: вход, сдача, результат** | 11b, 12 | Вход по личной ссылке, сдача, немедленный разбор, школьные отчёты. Опирается на 6–8 и 11a |
| **Выпуск** | 13 | Нагрузочная, визуальная и ручная приёмка, retention, документация |

M3a без M3b не выпускается: оплатившему гостю должен быть доступен вход на экзамен.

## Этап 2. Схема БД и домен проведений
Подробно: [`stage-02.md`](public-exam-feature/tasks/stage-02.md).
Зависимости: 0. Результат: таблицы, DTO, репозитории; минутный cron-запуск; без UI.

- [ ] 2.1 DDL: `exam_events` (статусы draft/published/completed, `variant_snapshot` JSON для неизменяемости, `guest_registration_enabled`), `exam_sessions`, `exam_participants`, `exam_participations`, `exam_registrations` (с `active_slot`), `exam_sources` (invitation_key_hash, generation, key_revoked_at), `exam_access_tokens` (purpose=invitation|entry|result|report), `exam_guest_sessions`, `exam_reports`, `exam_report_members`, `exam_events_outbox`, `exam_operation_keys`, `exam_guest_applications`, `exam_payment_links`, `exam_manual_resolutions` (SPEC §11). Таблицы гостей/оплаты/отчётов создаются сразу, наполняются в 11a/12. **Согласия**: гостей не собираем, используем существующую `consents` (как лид-форма); ученики с уже заполненными согласиями из школы (на `person_id`).
- [ ] 2.2 Расширение `assessment_attempts`: `exam_participation_id`, `exam_registration_id`, `student_person_id` nullable только для новых гостевых попыток; уникальность официальной попытки по участию.
- [ ] 2.3 DTO, Repositories (WPDB), `Clock`-зависимый сервисный слой по `ClockInterface`; время хранится в UTC-модели новых таблиц с адаптером к старым.
- [ ] 2.4 `ExamEventService`: создать/изменить/опубликовать/отменить проведение; жизненный цикл draft → published → completed (+ cancellation отдельно); сеансы с валидацией дат; вместимость сеанса = `RoomDTO.seats` выбранного кабинета (копия в `exam_sessions.capacity`), пересинхронизация при смене `seats`. Снимок варианта в `variant_snapshot` при публикации первого сеанса; правка опечатки перед следующим сеансом с пересборкой снимка.
- [ ] 2.5 `ExamAccessTokenService`: выдача, обмен (проверка `generation`), отзыв, обновление при перевыпуске ссылки (инкремент `generation`). Ключ ≥128 бит, в БД только хеш в `exam_access_tokens`.
- [ ] 2.6 **Минутный cron-запуск** (перенесён из 9.4): регистрация `every_minute` интервала в `CronController::register()`, запуск `CronHook::NotificationsTick->value` и новых `ExamAutoExpireTick`/`ExamHoldReleaseTick`. Выполняется раз в минуту, lock от параллелизма.
- [ ] 2.7 Миграция по `db-migrations`: DDL повторяемый, без дропа core-таблиц.

Проверка: PHPUnit (сервисы, валидации, токены); integration-тесты репозиториев на реальной MariaDB; миграция применяется дважды без потерь; cron выполняется по расписанию.

## Порядок и параллельность

```
0 → 1 ┐
0 → 2 (в т.ч. 2.6 cron) → 3 ┬→ 4 ┬→ 5 (M1)
                           │    └→ 6 → 7 → 8 → 9, 10 (M2)
                           └→ 11a (после 3 и 4, параллельно 5–8) ┐
                                             8 → 11b (нужны 6, 7, 11a) → 12 → 13
```

Этапы 1 и 2 независимы друг от друга и могут идти параллельно после 0; 2.6 (minuten cron) является инфраструктурой и нужен для 6.
