# План реализации

Порядок работ: 4 → 2/3 → 1 → 6 → 5. Сначала общий нормализатор ответа и формат
вывода (их трогают все остальные пункты), затем экраны, затем самое объёмное —

## 1. Правильный ответ у преподавателя — только для неверных

**Как сейчас.** `WorkDetailService` кладёт `correct` в КАЖДУЮ задачу и работы, и
экзамена (`inc/Services/Course/WorkDetailService.php:281`, `:297`, `:433`), а
`taskBlock()` рендерит блок «Правильный ответ» при любом вердикте
(`src/js/profile/work-review.js:353`). Ответ ученика уже человекочитаемый —
`CorrectAnswerResolver::formatStudentAnswer()`.

**Что менять.**
1. `src/js/profile/work-review.js:353` — блок `sum-task-correct` показывать
   только при `'correct' !== t.verdict` (то есть `incorrect` и `pending`: на
   ручной проверке эталон учителю нужен как раз до выставления балла). Блок
   «Ответ ученика» остаётся безусловным.
2. `WorkDetailService::attemptHistory()` (`:105-183`) `correct` не отдаёт вовсе,
   а прошлые раунды сдачи рендерятся тем же `taskBlock()` — эталон там просто
   пропадает. Добавить `'correct' => $this->correctAnswers->resolve( $taskId )`
   в строку задачи, чтобы экран не зависел от выбранной попытки.
3. Сервер продолжает отдавать `correct` всегда — фильтрация чисто на экране;
   эталон и так уходит только в teacher-facing колбэк.

**Проверка.** `tests/Unit/Services/Course/WorkDetailServiceTest.php` — эталон в
истории попыток; вручную: верная задача без блока эталона, неверная — с ним.

**Что менять.**
1. `CorrectAnswerResolver` — `implode( "\n", … )` в четырёх методах:

   (`src/scss/profile/components/_summary.scss:183`) — CSS там не трогаем.

matching/ordering в её составе нет, а `slots()` режет по `\s+` — перенос строки
для неё эквивалентен пробелу. Регрессия маловероятна, но лист ответов станции

## 4. Пробелы и переносы не влияют на сверку, но сохраняются в выводе

**Как сейчас.** Нормализация разная в пяти местах:
`TextAnswerChecker::normalize()` (`inc/Services/Task/Checkers/TextAnswerChecker.php:48-57`)
— регистр + `trim` + построчный `rtrim`, но пробелы ВНУТРИ строки значимы;
`TripleAnswerChecker` и `FillTextParser::checkGap()` — только `trim` + регистр;
`BatchCheckService:89` — `strtolower( trim() )` (даже не `mb_`);
`KegeResultSheetService::same()` (`:216-222`) — схлопывает `\s+` в один пробел.
Отсюда «Макс: 2; 3» и «Макс:2;3» — разные ответы.

**Что менять.**
1. Завести общий нормализатор — трейт `Inc\Shared\Traits\AnswerNormalizer`
   (`inc/Shared/Traits/`) со статическим `normalizeAnswer( string ): string`:
   `mb_strtolower` + удаление ВСЕХ пробельных символов
   (`preg_replace( '/\s+/u', '', … )` — сюда же попадают `\r\n`, `\t` и
   неразрывный пробел). Статический метод в трейте, потому что
   `FillTextParser::checkGap()` статический, а чекеры — DI-объекты; отдельная
   статическая утилита завела бы класс вне списка разрешённых в CLAUDE.md.
2. Подключить трейт и заменить локальную нормализацию в: `TextAnswerChecker`,
   `TripleAnswerChecker`, `FillTextParser::checkGap()`, `BatchCheckService`
   (сравнение подпунктов составного задания, `:89`) и
   `KegeResultSheetService::same()` — иначе лист ответов станции и чекер
   разойдутся в вердикте на одном и том же ответе.
   `MatchingChecker`/`OrderingChecker` сравнивают элементы, которые ученик
   выбирает из авторских списков, — там оставить `trim` + регистр.
3. Вывод не трогаем: `answer_text` пишется сырым
   (`SubmissionService::submitBatch()`), `CorrectAnswerResolver` режет только
   края. Схлопывание переносов сейчас чисто CSS-ное и лечится тем же
   `white-space: pre-wrap` на `.ansbox` из пункта 2-3 — это обязательная часть
   пункта 4, а не косметика.
4. Убедиться, что `trim()` в `studentTriple()`/`studentFill()`/`studentMatching()`
   режет только края значения, а не внутренние переносы (сейчас так и есть).

**Принятое следствие.** Ответы, где пробел разделял два значения («1159 57»),
станут совпадать и слитно («115957»). Это прямое требование задачи;
альтернатива «схлопывать пробелы вместо удаления» не покрывает пример
«Макс: 2; 3» ↔ «Макс:2;3», поэтому выбрано удаление.

**Проверка.** Новый `tests/Unit/Shared/AnswerNormalizerTest.php` + кейсы в
`TextAnswerCheckerTest` (завести, если нет) и `BatchCheckServiceTest`:
«Макс: 2; 3», «Макс:2;3», «Макс:\n2;3», « макс : 2 ; 3 » — все верны. Плюс кейс
«вывод сохраняет исходный вид» в `WorkDetailServiceTest`.

## 6. Ручной зачёт задания на странице проверки

**Как сейчас.** Форма оценки задачи рендерится только для ручных шаблонов:
`canGrade` (экзамен) и `canGradeSubmissionTask` (работа) требуют `t.manual` /
`t.gradable`, то есть `TaskTemplate::isFileAnswerShape()`
(`src/js/profile/work-review.js:315-322`). Для автопроверяемой задачи учитель не
может сделать ничего, кроме возврата всей работы.

### Этап A — работы (submission), основной сценарий из задачи

Бэкенд почти готов: `SubmissionService::gradeBatchTask()` (`:297-311`) пишет
score/status в per-task строку и пересчитывает агрегат, гейта на «ручной шаблон»
ни в нём, ни в `BatchSubmissionCallbacks::ajaxGradeBatchTask()` (`:105-131`) нет;
`WorkDetailService::fromSubmission()` уже отдаёт `task_submission_id` для каждой
задачи, у которой есть строка сдачи.

1. **JS.** В `taskBlock()` для `d.kind === 'work'` и любой задачи с
   `t.task_submission_id`, у которой `'correct' !== t.verdict`, рендерить
   компактную кнопку «Засчитать» (класс `stg-credit`); для ручных задач она
   встаёт рядом с существующей формой, дублировать форму не нужно. Обработчик —
   в `wireSubmissionTaskGrading()` (`:474`): тот же `batchGradeApi('gradeTask')`
   со `score = t.max_score ?? 1`, `feedback` не трогаем.
2. **Снимок агрегата.** `gradeBatchTask()` обязан обновлять и JSON-снимок
   вердиктов в `answer_text` агрегатной строки — иначе ученик в плеере
   продолжит видеть «Неверно»: экран результатов работы читает именно его
   (`LessonPlayerService::currentSubmission()`, `:290-298` →
   `src/js/player/step-work.js::renderResults()`). Добавить приватный
   `syncAggregateSnapshot( … )` и звать его перед `recalculateAggregate()`.
   Сам `recalculateAggregate()` (`:369-410`) правок не требует — он считает по
   per-task строкам.
3. **Метка «засчитано вручную».** Новой колонки не нужно: авто-проверка при
   сдаче пишет строку без `graded_by_user_id` (`submitBatch()`, `:167-189`),
   поэтому `graded_by_user_id IS NOT NULL` — надёжный маркер вмешательства
   учителя. Отдавать его из `WorkDetailService` как `manually_graded` и рисовать
   бейдж «Засчитано преподавателем» рядом с вердиктом: зачёт должен быть отличим
   от авто-вердикта в аудите и на пересдаче.
4. Права и нонс уже на месте: `Nonce::GradeBatch` + `Capability::ManageLmsTeaching`
   + `canWriteJournal()` по группе.

### Этап B — экзамены (attempt)

`GradeAttemptCallbacks::ajaxGradeAttempt()` (`:67-79`) намеренно запрещает ручной
балл автопроверяемому заданию: лист ответов станции
(`KegeResultSheetService::assemble()`, `:126` и `:204-222`) пересчитывает балл
сличением с эталоном и ручной игнорирует — иначе журнал и лист покажут разные
итоги (это уже чинили 2026-08-21).

Поэтому «засчитать» для экзамена делать ТОЛЬКО вместе с починкой листа:
1. Снять запрет для явной операции «засчитать» (`score = max_score`,
   `is_correct = 1`), оставив его для произвольного балла.
2. `KegeResultSheetService::assemble()` — брать балл из строки ответа, если у
   неё проставлен `graded_by_user_id` (тот же маркер, что в Этапе A), и только
   иначе считать `slotScore()` по эталону. Сейчас `$graded` заполняется лишь для
   заданий с пустым эталоном — расширить.
3. `AutoGradeService::finalize()` (`:39-61`) суммирует сохранённые строки и
   ручной балл не затирает — правок не требует. Но `gradeAttempt()` при
   пересдаче перезапишет строки авто-вердиктом; это корректно (новая попытка —
   новый ответ), проверить, что зачёт не «прилипает» к следующей попытке.

Если Этап B не влезает в релиз — выпускать Этап A отдельно: в задаче речь про
«работу», ЕГЭ-станция туда не попадает.

**Проверка.** `SubmissionServiceTest` — зачёт авто-задачи меняет per-task строку,
снимок агрегата и итог работы; `WorkDetailServiceTest` — флаг `manually_graded`;
`KegeResultSheetServiceTest` — ручной зачёт побеждает эталон (Этап B). Ручной
прогон: засчитать задачу → у ученика в плеере вердикт «Верно», в журнале новый
балл, работа не возвращалась.
