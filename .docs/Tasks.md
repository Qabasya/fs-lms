## План по п.3 — AdSync: WP сам отправляет задания на сервер в офисе (push)

### Схема
```
Сайт (WP) ──HTTPS POST──▶ белый IP офиса :порт ──проброс──▶ контейнер Python (11.11.11.22)
                                                              └─LDAPS─▶ контроллер домена
```
Сейчас модуль работает наоборот: Python сам забирает задания с сайта (`GET /ad/jobs` + `POST /ad/ack`).
После переделки сайт шлёт задание сам и в том же ответе получает результат. Входящие
REST-эндпоинты модуля на сайте удаляются: у сайта становится на одну публичную точку входа меньше.

### Что остаётся как есть
- Очередь `ad_outbox` (своя таблица модуля): задание сначала пишется в очередь, потом
  доставляется. Если сервер в офисе недоступен (свет, интернет, перезагрузка Proxmox), задание
  не теряется и уйдёт при следующей попытке.
- Бэкофф ретраев (1м → 2м → … → 1ч, после 6 неудач — «мёртвое»), `idempotency_key`, события
  (заявка создана → provision; заявка истекла/в корзину, ученик отчислен → deprovision).
- Пароль не хранится в очереди: он читается из заявки в момент отправки.
- Спиннер на форме заявки со статусом «Создаём учётную запись в домене…» — теперь он просто
  быстрее доходит до «готово».

### Этап 0. Узнать исходящий IP сайта
Исходящий IP — адрес, с которого сервер хостинга сам ходит в интернет (именно он придёт на
роутер офиса, когда сайт отправит задание). На виртуальном хостинге Beget он **не обязательно
совпадает** с адресом сайта `87.236.16.76`: сайты живут на общем сервере, у которого свой
исходящий адрес. Поэтому его не угадываем, а измеряем:
1. Через SSH на Beget (панель → «SSH»):
   `curl -s https://ifconfig.me ; echo ; curl -s https://api.ipify.org`
   Оба сервиса должны вернуть один и тот же адрес — это он.
2. Если SSH нет — спросить поддержку Beget: «с какого IP уходят исходящие соединения сервера,
   на котором размещён future-step.ru». Там же спросить, **разрешены ли исходящие соединения на
   нестандартные порты** (некоторые хостинги режут всё, кроме 80/443) — от ответа зависит порт.
3. Проверка после настройки роутера (там же, в SSH):
   `curl -vk https://92.101.127.156:<порт>/v1/health` — должно ответить; с телефона по мобильному
   интернету тот же адрес открываться **не** должен.
Адрес может смениться при переезде сайта на другой сервер Beget — тогда доставка встанет
(сайт увидит это: «последняя успешная доставка» в настройках модуля), и правило на роутере
нужно обновить.

### Этап 1. Роутер Keenetic Hopper (KeeneticOS 4.x, веб-интерфейс)
Названия пунктов меню — по KeeneticOS 4.x; в других версиях могут немного отличаться.

1. **Постоянный адрес контейнера.** Если `11.11.11.0` раздаёт DHCP роутера: «Список устройств»
   → контейнер → «Постоянный IP-адрес» = `11.11.11.22`. Если адрес задан статикой в Proxmox —
   просто убедиться, что он вне DHCP-пула сегмента.
2. **Освободить порт на внешнем интерфейсе.** «Пользователи и доступ» → «Удалённый доступ»:
   если включён веб-доступ к роутеру из интернета по 443 — отключить или перенести на другой порт.
   Роутер не должен занимать порт, который пробрасываем.
3. **Проброс порта.** «Сетевые правила» → «Переадресация» → «Добавить правило»:
   - Описание: `AdSync`
   - Вход: интернет-подключение провайдера (то, на котором `92.101.127.156`)
   - Выход: «IP-адрес» → `11.11.11.22`
   - Протокол: TCP
   - Тип: одиночный порт, внешний порт `8443` (или `443`, если Beget режет нестандартные),
     порт назначения `8443`
   - Расписание: «Работает постоянно»
4. **Пускать только сайт.** «Сетевые правила» → «Межсетевой экран» → вкладка интернет-подключения
   провайдера → два правила **в этом порядке**:
   1) Разрешить · TCP · IP-адрес источника = `87.236.20.5` · IP назначения
      `11.11.11.22` · порт назначения `8443`
   2) Запретить · TCP · источник — любой · IP назначения `11.11.11.22` · порт назначения `8443`
   Правила межсетевого экрана Keenetic для переадресованного трафика задаются с **локальным**
   адресом и портом назначения (как в примерах выше). Обязательно проверить результат с чужого
   адреса (Этап 0, п.3): порт должен быть закрыт.
5. **Сегмент сервера (желательно).** Если `11.11.11.0` — отдельный сегмент («Мои сети и Wi-Fi»
   → «Сегменты»), в межсетевом экране этого сегмента контейнеру достаточно доступа к контроллеру
   домена (LDAPS, TCP 636) и в интернет к NTP/обновлениям; остальную офисную сеть ему видеть
   не нужно.
6. **Проверка изнутри офиса не показательна.** Обращение из офиса на `92.101.127.156` может не
   пройти (NAT loopback) или обойти правила — проверять только снаружи.

### Этап 1б. Сертификат на сервере в офисе
Let's Encrypt у сайта здесь ни при чём: он защищает соединение браузер → сайт. В нашей схеме
сайт сам выступает клиентом и подключается к серверу в офисе, поэтому сертификат нужен
**серверу в офисе**.
- **Рекомендую: самоподписанный сертификат с IP `92.101.127.156` в SAN** (срок — лет 10).
  Файл сертификата (`.crt`, без ключа) кладётся на сайт, путь — константой в `wp-config.php`,
  и `wp_remote_post` доверяет **только ему** (`sslverify` + `sslcertificates`). Это строже
  обычного сертификата: подменить сервер нельзя даже чужим валидным сертификатом. Домен,
  открытый 80-й порт и продление не нужны.
- Альтернатива: поддомен `ad.future-step.ru` → `92.101.127.156` + Let's Encrypt через DNS-01
  (по HTTP-01 не выйдет — для проверки пришлось бы открыть 80-й порт всему интернету).
  Минус — продление раз в 90 дней и автоматизация DNS-записей Beget.
- Контейнеру — синхронизация времени (chrony): подпись запроса привязана ко времени.

**Как выпустить самоподписанный сертификат** (всё — в контейнере `11.11.11.22`, нужен только
`openssl`: `apt install openssl`, если его нет):
```bash
mkdir -p /etc/adsync/tls && cd /etc/adsync/tls
openssl req -x509 -newkey rsa:3072 -sha256 -days 3650 -nodes \
  -keyout server.key -out server.crt \
  -subj "/CN=adsync-office" \
  -addext "subjectAltName=IP:92.101.127.156" \
  -addext "basicConstraints=critical,CA:TRUE"
chmod 600 server.key
openssl x509 -in server.crt -noout -subject -ext subjectAltName -enddate   # проверка
```
- `server.key` (закрытый ключ) **никогда не покидает контейнер**, его читает только
  Python-сервер (`uvicorn ... --ssl-keyfile server.key --ssl-certfile server.crt`).
- `server.crt` (открытая часть) копируется на Beget **выше `public_html`**, чтобы его нельзя
  было скачать по ссылке, напр. `~/future-step.ru/adsync-server.crt`, и прописывается в
  `wp-config.php`: `define( 'FS_LMS_AD_SERVER_CERT', __DIR__ . '/../adsync-server.crt' );`
  (точный путь уточнить по раскладке каталогов на Beget).
- В SAN стоит именно `92.101.127.156`: сайт подключается по этому адресу, и проверка имени
  сертификата должна совпасть.
- Проверка с Beget по SSH (после Этапа 1 и запуска сервера):
  `curl --cacert ~/future-step.ru/adsync-server.crt https://92.101.127.156:8443/v1/health`
  — ответ без `-k` означает, что сертификат принят.
- Смена сертификата (утёк ключ, сменился IP): выпустить заново той же командой и заменить
  файл на сайте. Срок — 10 лет, продлевать не нужно.

### Этап 2. Python-сервис (из поллера — в маленький HTTP-сервер)
1. FastAPI/uvicorn (или aiohttp), systemd `Restart=always` / autostart контейнера в Proxmox.
2. Эндпоинты:
   - `POST /v1/jobs` — одно задание (`provision`/`deprovision`), ответ синхронный:
     `{status: done|failed, error?, sam_account_name?}`. Создание учётки в AD занимает доли
     секунды, поэтому отдельный обратный вызов на сайт не нужен.
   - `POST /v1/reconcile` — сайт присылает список активных логинов (раз в сутки), сервис
     отключает в управляемых OU всех, кого нет в списке. Первое время — режим «только лог».
   - `GET /v1/health` — для кнопки «Проверить соединение» в админке.
3. Проверка каждого запроса: HMAC от `метод + путь + timestamp + тело`, окно по времени,
   запоминание `idempotency_key` (повтор того же задания → тот же ответ, без повторного создания).
4. Карта `subject_key → OU` (`inf_ege`, `inf_oge`), DN `OU=Отчисленные`, сервис-аккаунт — в `.env`.
   Пароли в логах не пишутся.

### Этап 3. Сайт (модуль `Inc\Modules\AdSync`)
1. **Отправитель** `AdDeliveryService`: берёт готовые задания из очереди, подписывает, шлёт

2. **Когда отправлять:**
   - сразу после создания задания — на `shutdown`, после того как ответ пользователю уже
     отдан (`fastcgi_finish_request()`), чтобы форма заявки не ждала офис;
   - ретраи и хвост очереди — WP-cron раз в минуту (новый интервал в `CronManager`). Так как
     WP-cron срабатывает только от посещений, на хостинге лучше системный cron на `wp-cron.php`
     или WP-CLI-команда `wp fs-lms ad flush` (заодно для ручного прогона).
   - блокировка (транзиент-лок модуля), чтобы два процесса не отправили одно задание дважды.
3. **Сверка:** ежедневный cron → `POST /v1/reconcile` со списком из `AdReconcileService`
   (сам сервис уже есть).
4. **Удалить:** `AdSyncRestController` (`/ad/jobs`, `/ad/ack`, `/ad/active-usernames`),

5. **Настройки** (секция «Синхронизация с доменом»): адрес сервера (`https://<белый IP>:8443`),

   кнопка «Повторить мёртвые». Секрет HMAC и отпечаток сертификата — константами в `wp-config.php`.
6. Документация: переписать `.docs/AdSyncPythonService.md` и раздел AdSync в `.docs/FS_LMS_API.md`

### Этап 4. Ввод в строй
1. «Проверить соединение» из админки → зелёный.
2. Тестовая заявка → учётка в нужной OU за секунды → вход на ПК в офисе.
3. Тестовое отчисление → учётка в `OU=Отчисленные`, отключена.
4. Выключить сервер в офисе → подать заявку → включить → задание доехало из очереди само.
5. Сверка в режиме «только лог» неделю → включить отключение.
6. Разобрать старые «мёртвые» задания со времён простоя модуля.
