# Сводка по ученику — план доработки

Ориентир — мокап `.docs/07-student.html` (LMS 2.0), но в упрощённом виде: без карточки
профиля (ФИО/доступ и т.п. — их и так не показываем), без плиток-счётчиков (KPI),
без выбора периода/роли (это демо-переключатели мокапа). Оставляем только:

1. Выбор ученика.
2. Выбор его курса/направления (группы) — показывается, только если у ученика их больше одного.
3. Две вкладки: **«Занятия и прогресс по урокам»** и **«Работы»**.

## Текущее состояние (для контекста)

- Экран — постоянный пункт левого меню личного кабинета преподавателя (`TeacherProfileView.php`,
  `screens.summary`), рендерится SPA-кодом `src/js/profile/summary.js`, без PHP-шаблона.
- Выбор **сейчас идёт от группы**: пикер группы → ростер → первый ученик ростера по умолчанию.
  Переключение группы сбрасывает ученика. Обратного пути «выбрал ученика → увидел его группы»
  нет.
- Backend: `StudentSummaryService::forStudent(groupId, personId)` — всегда в рамках одной
  группы. Отдаёт список занятий (групповые + личные индивидуальные), посещаемость
  (`AttendanceService`), и работы по занятию (`GradebookService::forGroup()` →
  `badge/value/display/title/source_type/source_id/overdue`).
- **Прогресса по шагам урока в сводке нет.** Сервис для него уже есть и не требует
  переделки — `LessonProgressService::getStepStatuses()` / `isLessonCompleted()` — просто
  не подключён к `StudentSummaryService`.
- Вкладки «Работы» тоже нет — есть только список работ внутри карточки занятия
  (`.sum-works`), без общей таблицы и без данных вне контекста занятия
  (score/maxScore/category/gradedAt в JSON сейчас не отдаются, хотя в
  `GradebookEntryDTO` уже есть).
- AJAX: `GetStudentSummary` (group_id + student_person_id) — JSON, без HTML.

## Решения по неоднозначным местам (чтобы не блокироваться)

- **Скоуп вкладки «Работы»** — в рамках выбранного курса/группы, как и вкладка занятий
  (а не «все работы ученика по всем курсам сразу»). Это проще, согласуется с тем, что
  весь экран уже привязан к паре group+student, и не ломает права доступа
  (`GroupAccessGuard::canManage`) на группу, в которой ведёт именно этот преподаватель.
  Если позже понадобится кросс-курсовая сводка — под неё уже готов
  `GradebookService::forStudent()`.
- **Прогресс урока в списке занятий** — не поштучно по каждому шагу (это было бы
  избыточно детально для списка), а компактно: счётчик «done/open» + индикатор проблем
  (есть ли `fail`), как значение в строке таблицы. Поштучные квадратики шагов, как в
  мокапе, — не делаем, чтобы не усложнять фронт; при необходимости добавить это отдельной
  итерацией.

## Backend

### 1. Курсы (группы) конкретного ученика — новый метод + AJAX

Нужен способ получить группы ученика, доступные текущему преподавателю, чтобы построить
переключатель курса.

- `StudentRecordRepository::findActiveByStudent(personId)` уже отдаёт все активные записи
  зачисления (group_id, subject и т.п.) — источник данных есть.
- Добавить метод (например, в `GroupRosterService` или новый узкий сервис
  `StudentCoursesService`): `forStudent(int $personId, int $teacherId): array` —
  пересечение групп ученика с группами, доступными преподавателю
  (та же логика прав, что в `ReviewQueueService::groupIdsFor()` —
  `findByTeacherId` + активные замены через `SubstitutionRepository`).
  Возвращает `[{group_id, name}]`.
- Новый кейс `AjaxHook::GetStudentCourses`, обработчик — `ajaxGetStudentCourses()` в
  `GroupRosterCallbacks` (authorize тем же `Nonce::SaveSchedule` + `Capability::ManageLmsTeaching`,
  по аналогии с `ajaxGetStudentSummary`).

### 2. Поиск/выбор ученика без обязательного знания группы

Сейчас ученика находят только через ростер выбранной группы. Для «выбрать сначала
ученика» нужен способ найти ученика по имени среди **всех** учеников, доступных
преподавателю (across his groups), без выбора группы вручную.

- Практичный минимум: переиспользовать существующий ростер-подход, но агрегированно —
  собрать ростеры всех доступных преподавателю групп (`groupIdsFor()`-подобная логика уже
  есть в `ReviewQueueService`, можно вынести общий метод в один сервис/трейт, раз он
  используется и там, и здесь — избежать дублирования кода доступа к группам).
- Новый AJAX `GetTeacherStudents` (или расширить существующий `GetGroupRoster`, если он
  и так работает по списку групп) — отдаёт `[{person_id, name, groups:[group_id...]}]` для
  клиентского поиска по фамилии (без вызова на каждый ввод — фильтрация на фронте, как в
  мокапе `oninput`).
- Если преподаватель ведёт мало групп (типичный случай), объём этого списка небольшой —
  отдельный поиск через AJAX по мере ввода не нужен, простой JS-фильтр по уже
  загруженному списку достаточен.

### 3. Прогресс по урокам в `StudentSummaryService`

- Внедрить `LessonProgressService` в конструктор `StudentSummaryService`.
- Для каждого занятия (`group_lesson_id`), где есть `lessonId`, посчитать
  `getStepStatuses($personId, $groupLessonId)` и добавить в строку занятия агрегат:
  `progress: {total, done, failed, open}` (`open` — статусы не `Locked`; сама
  `LessonProgressService` уже не отдаёт «locked»-шаги в принципе, т.к. это фронтовое
  понятие мокапа для «занятие ещё впереди по расписанию» — здесь просто не считаем
  шаги занятий, которых у ученика ещё не было/не открыто).
- Для уроков без `lessonId` (label-занятия) — `progress: null`, фронт показывает прочерк.
- Для открытых групп (`AccessMode::Open`, `$isOpen`) прогресс не считаем — тоже `progress: null`
  (зафиксировано: не нужен по продуктовому смыслу открытых групп).

### 4. Данные для вкладки «Работы»

- В `StudentSummaryService::forStudent()` (или отдельным методом того же сервиса,
  чтобы не раздувать один ответ, если объём данных большой — решить на этапе
  реализации после замера) добавить работы с расширенным набором полей из
  `GradebookEntryDTO`, которых сейчас нет в ответе: `category`, `score`, `maxScore`,
  `gradedAt`, `groupKey` (нужен, если у работы возможно несколько попыток и хотим их
  сворачивать/показывать последнюю).
- Дедлайн сдачи (`due date`) — отдельный источник (`GetWorkDeadlines`/`SaveWorkDeadlines`),
  в `GradebookEntryDTO` его нет. **Не подключаем** в этой итерации (в мокапе это колонка
  «Срок сдачи» — decorative, не критично для функциональности); дедлайн и так виден как
  «просрочено» через `overdue`.
- «Попытки» (count) — в текущих DTO/сервисах такого поля нет, подсчёт потребовал бы
  дополнительного запроса к `submissions`/`attempts`. Не делаем в этой итерации — за
  рамками «не сильно усложняя».

## Frontend (`src/js/profile/summary.js`)

1. **Смена порядка выбора**: сначала пикер ученика (список всех учеников преподавателя,
   с JS-фильтром по вводу — переиспользовать компонент `picker.js`, как сейчас
   переиспользуется для группы/ученика), затем — если у выбранного ученика больше одной
   группы — пикер курса; если группа одна, показываем её как подпись без селектора
   (как в мокапе `enc.sel`/`enc` без `sel`).
2. **Вкладки**: простой таб-бар (2 кнопки, как в существующем `works.js` для
   pending/confirm/done — переиспользовать тот же паттерн переключения `.pane.on`),
   без счётчиков-плашек KPI.
3. **Вкладка 1 «Занятия и прогресс по урокам»**: текущий список карточек занятий
   (`lessonCard()`) остаётся, добавляется индикатор прогресса урока (`done/open`,
   с акцентом, если есть `failed`) рядом с посещаемостью.
4. **Вкладка 2 «Работы»**: новая простая таблица/список (без пагинации, объём на
   ученика небольшой) — тип работы, тема урока, дата, статус, балл; клик по строке →
   существующий `openWorkReview(sourceType, sourceId)` (уже используется из
   `summary.js` и `works.js`, менять не нужно).
5. Профиль-карточку и KPI-плитки в текущей вёрстке добавлять не нужно — их и так нет,
   в этом смысле фронт уже соответствует упрощённому мокапу.

## Порядок работ и оценка

| # | Шаг | Оценка |
|---|-----|--------|
| 1 | Метод + AJAX «курсы ученика» (`StudentCoursesService`/аналог, `GetStudentCourses`) | 0.5 дня |
| 2 | Метод + AJAX «ученики преподавателя» для стартового пикера (переиспользовать/выделить общую логику доступа к группам из `ReviewQueueService`) | 0.5 дня |
| 3 | `LessonProgressService` → `StudentSummaryService`: агрегат прогресса по занятию | 0.5 дня |
| 4 | Расширение отдаваемых полей по работам (`category/score/maxScore/gradedAt`) | 0.25 дня |
| 5 | Фронт: разворот порядка выбора (ученик → курс), пикер ученика с фильтром | 0.5–1 день |
| 6 | Фронт: таб-бар, вкладка «Занятия и прогресс» (индикатор прогресса в карточке) | 0.5 дня |
| 7 | Фронт: вкладка «Работы» (таблица + переход в работу) | 0.5 дня |
| 8 | Ручное тестирование (роли/группы/замены, ученик в 2+ группах, урок без `lessonId`, работа без дедлайна/попытки) + правки | 0.5 дня |

**Итого: ~3.5–4.5 дня** одного разработчика, без учёта код-ревью и правок по замечаниям.

## Зафиксированные ограничения (реальные объёмы, подтверждено пользователем)

- У преподавателя — до 6 групп, в группе — до 10 учеников. Т.е. стартовый список
  «ученики преподавателя» — до ~60 записей максимум. Клиентский JS-фильтр по уже
  загруженному списку (без AJAX-поиска по вводу) достаточен, отдельный
  AJAX-поиск не нужен — риск снят.
- Для открытых групп (`AccessMode::Open`) прогресс по урокам **не показываем**:
  `progress: null` для всех занятий такой группы (как и для label-занятий без
  `lessonId`) — не подключаем `LessonProgressService` для этого случая, дополнительно
  проверять поведение прогресса на открытых группах не нужно.
