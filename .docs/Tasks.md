## П1. Код ошибки `X-CONFLICT` в `delete_exam_session` (задача «Попытка удаления…»)

**Причина.** `ErrorCode::ExamConflict` («Экзамен: пересечение с другим») использован как универсальный «отказ по состоянию». В `ExamEventService` им помечены 20+ разных причин: «Сеанс не найден», «Сеанс завершён», «В сеансе есть записи», «Опубликовать можно только черновик», «Укажите причину переноса», «Дата вне периода», ещё `ExamConductCallbacks:124` (диапазон продления) и `GradeAttemptCallbacks:214`. Подпись «пересечение» верна только для реальных пересечений (кабинет/время).

**Решение (без дробления на десятки кодов).**
1. В `ErrorCode` добавить два кейса и подписи в `label()`:
   - `ExamNotFound = 'X-NOT-FOUND'` — «Экзамен: запись не найдена» (все «Сеанс/Вариант не найден»);
   - `ExamState = 'X-STATE'` — «Экзамен: действие недоступно в этом состоянии» (завершён, есть записи, не черновик, идут уведомления, сеансы вне периода, снимок менять нельзя, нет сеансов в будущем).
2. `ExamConflict` оставить только для настоящих пересечений (кабинет/время). Валидацию ввода («Укажите причину», «Задайте время…», диапазон продления) — на существующий код ввода, если есть, иначе тоже `ExamState`. Перед заменой: `grep -rn "ErrorCode::ExamConflict" inc` (≈25 мест), пройти каждое и выбрать код по смыслу.
3. Проверить зависимости по коду: `inc/Cli/ExamStandCommand.php` (строки ~387, 454, 854 сопоставляют `ExamConflict` со строкой `conflict`) — добавить новые коды в маппинг, иначе стенд гонок изменит поведение. Обновить тесты, где ожидается `ExamConflict`.
4. Тест: `deleteSession` с записями → `ExamState`; без сеанса → `ExamNotFound`. В `tasks/README.md` §7 (контракт имён) дописать новые коды; в `inc/Services/Exam/CLAUDE.md` — правило «ExamConflict = только пересечение».
5. Старые записи журнала «Ошибки» с `X-CONFLICT` остаются как есть (миграция не нужна).

## П7. Журнал «Экзамены» (задача 1 + вопрос о таблицах)

### Ответ на вопрос «одна таблица, несколько или распределить по существующим»

**Рекомендация: один новый канал `LogChannel::Exams` с одной таблицей `exam_log`.**

- Все события — одна сущность «действие над объектом экзамена»: актор + действие + объект (проведение/сеанс/заявка/попытка/платёж) + результат + контекст. Разные только поля контекста → JSON-колонка `context`, как в других каналах.
- Несколько таблиц (по группам: работа/сеансы/заявки/платежи) дадут N репозиториев, N вкладок и N фильтров при том, что смотреть журнал хочется хронологически по одному сеансу или заявке («что происходило с заявкой №X»). Это решается фильтрами по `event_id`/`session_id`/`registration_id`, а не таблицами.
- Распределять по существующим не подходит: `EntityAudit` — про CRUD сущностей WP и не знает гостей (актор — не пользователь WP), `Errors` — только сбои, `LearningEvents` — про учебный прогресс курса, а экзаменные попытки по правилам проекта **не должны** смешиваться с курсовыми выборками. Ошибки по-прежнему остаются и в «Ошибки» (`ErrorCode`), в «Экзамены» пишется бизнес-контекст — дубль допустим только для технических сбоев попытки (см. ниже), с общим `ref`.
- Единственное исключение, которое стоит оставить в существующем канале: **поступление оплат** — если платёж уже фиксируется в журнале WooCommerce/Email, в «Экзамены» писать только связанное с экзаменом событие («оплата заявки получена → допуск»), без дублирования платёжных данных.

### Модель

- Миграция (скилл `db-migrations`): таблица `exam_log` — `id`, `created_at` (UTC), `action` (enum, varchar), `actor_type` (`user|guest|system`), `actor_user_id` NULL, `actor_label` (ФИО/«гость»), `event_id`, `session_id`, `registration_id`, `participation_id`/`attempt_id` — все NULL, `result` (`success|failure`), `ip`, `context` JSON/longtext. Индексы: `(event_id)`, `(session_id)`, `(registration_id)`, `(action)`, `(created_at)`. ФИО участника писать, если известно, иначе только ID; телефон, email и токен ссылки гостя — не писать (см. «Решения по открытым вопросам»).
- `LogChannel::Exams` (+`label()`/`tableName()`), `ExamLogAction` (enum `Inc\Enums\Exam\`, с `label()`), `ExamLogRepository extends AbstractLogRepository` (`filterMap`: action, event_id, session_id, registration_id, actor_user_id, result; `Number`/`Text`), `ExamLogDTO`/`ExamLogInputDTO`.
- Вкладка «Экзамены» в «Логи» — по образцу `logs-8-auth.php` (фильтры, пагинация, CSV); регистрация вкладки/канала там же, где остальные (через `LogChannel::cases()`; проверить `LogsController`).

### Запись событий — подписчик, а не вызовы из сервисов

Образец — `EntityAuditSubscriber`/`EmailSubscriber`: `ExamLogSubscriber` (Controllers/Subscribers) слушает доменные события и пишет через `ExamLogService`. Сначала посмотреть, что уже публикует `ExamEventService`/`ExamOutbox` (outbox-события: отмена, перенос, допуск) и экшены WP (`do_action`) — переиспользовать; где события нет — добавить `do_action( 'fs_lms_exam_logged', ExamLogAction, $ctx )` в точку изменения состояния сервиса (одна строка, не логика). Список:

| Действие | Точка |
|---|---|
| создание/правка/публикация экзамена (работы), проведения | `ExamEventService::saveEvent/publishEvent` |
| создание/правка/удаление/отмена/перенос сеанса | `saveSession/deleteSession`, отмена и перенос |
| действия с заявками (запись, отмена, перенос, допуск, неявка) | сервис регистраций + `ExamTickService` (неявка — actor `system`) |
| допуск к экзамену | сервис допуска |
| начало/окончание попытки | сервис старта/сдачи попытки |
| технические ошибки (закрылась вкладка, вылетела сессия) | клиентский сигнал на сервер (см. ниже) + серверный timeout попытки |
| поступление оплаты | хук WooCommerce, который уже связывает платёж и заявку |
| копирование ссылки входа гостя | AJAX-колбек «лог действия» (JS-клик) |
| проверка работы ОГЭ преподавателем | `GradeAttemptCallbacks`/`ExamApprovalService` |
| открытие формы записи по ссылке преподавателя | рендер формы гостя; **не на каждый GET**: дедуп по IP+ссылка за N минут через `RateLimitService`-подобный механизм, иначе журнал забьют боты |

- Отдельно проверить два «клиентских» события: «копирование ссылки» и «закрылась вкладка / вылетела сессия» — они возникают в браузере. Нужен один лёгкий AJAX-экшен `AjaxHook::LogExamClientEvent` (nonce + ограниченный whitelist действий из `ExamLogAction`, лимит частоты; для гостя — nopriv + сессия `GuestSessionService`). Вкладка закрылась: `navigator.sendBeacon` на `pagehide`; сервер дополнительно фиксирует `heartbeat timeout` по уже существующему механизму попытки, если он есть (выяснить в `Services/Exam`), иначе событие только клиентское и помечается как «со слов клиента».
- Не блокировать пользовательский сценарий: запись в журнал в `try/catch`, сбой — `PluginLogger::warning`, транзакции экзамена журналом не расширять (запись **после** коммита, не внутри блокировок — иначе нарушится порядок блокировок из `Exam/CLAUDE.md`).
- Время — UTC, отображение через `ExamTime`.

### Этапы П7
1. Миграция + `LogChannel::Exams` + enum действий + репозиторий/DTO + вкладка (пустая, с фильтрами) + тесты репозитория.
2. `ExamLogService` + подписчик; серверные события: проведения, сеансы, заявки, допуск, неявка.
3. Попытки: старт/окончание, проверка ОГЭ, оплаты.
4. Клиентские события (ссылка гостя, технические ошибки) + дедуп открытия формы.
5. Ретенция: подключить канал к существующей очистке логов (проверить `LogRetention*`/cron), чтобы таблица не росла бесконечно.
6. Документация: `tasks/README.md` §7, `inc/Services/Exam/CLAUDE.md`, раздел логов в основном `CLAUDE.md` (число каналов).

## Решения по открытым вопросам

1. Вкладка «Работы» показывает только прошедшие занятия — как и «Занятия и прогресс» (общий фильтр в `forStudent()`).
2. Работ будущих уроков нет, статус «Ещё не открыта» не нужен; отдельный случай — не наступивший дедлайн у работы прошедшего урока (П2, п. 3).
3. П7: в журнал пишем ФИО участника, если оно известно (согласия на обработку есть); нет ФИО — только ID заявки/участника. Следствия: поле `actor_label`/`subject_label` в `exam_log` остаётся; CSV-экспорт журнала экзаменов — по стандарту выгрузки ПД: `authorizeAll()` с `ManageLmsPlatform` + `ExportPII`; просмотр вкладки — как у журналов с ПД (`PiiAccess`-журналирование просмотра/выгрузки проверить по аналогии с `students`). Токен ссылки гостя, телефон и email в журнал по-прежнему не пишем — только ФИО и ID. Поиск по ФИО — фильтр `Like` из П6 (делаем П6 раньше П7).
