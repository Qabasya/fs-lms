# BugFix
1. Фикс формы входа

- Скрытый адрес не защищает. Форма /sign-in/ отправляется на wp-login.php. Переадресация прячет только страницу, а бот шлёт POST прямо на wp-login.php.
- Нет лимита неудачных входов. Плагин только записывает их в журнал, в RateLimitService счётчика входов нет.
- Логины видны всем: /wp-json/wp/v2/users отдаёт обоих пользователей, включая id 1, а /?author=1 переадресует на страницу автора с логином. То есть половина пары «логин-пароль» уже известна.
- Капчи на форме входа нет. xmlrpc.php хостинг закрыл (405) — это хорошо.

Нужно защитить сайт от долбёжки ботов и взлома.
Минимальный набор:
1. Лимит неудачных входов по IP и логину, например 3 за 15 минут (предупреждай если осталась последняя попытка входа).
2. Скрыть список пользователей в REST для гостей и закрыть ?author=.
3. Невидимая капча на входе — в плагине уже есть модуль SmartCaptcha. (убедись, что есть параметр  invisible: true)

2. Проверь почему страницы статей (и задач видимо /tasks/) имеют ширину 1160 а не 1200 пикселей. Есть возможность исправить

3. Починить капчу плагина (модуль SmartCaptcha): включённый модуль падает с фатальной ошибкой. Капча темы на лид-формах уже работает — сверить с её реализацией.

4. На форме `/apply/` жёстко скрыть значок Яндекса о политике обработки данных (`SmartCaptcha-Shield-PrivacyLink`).

## 3. Починка капчи плагина (модуль SmartCaptcha)

**Как устроено сейчас.** На сайте две независимые капчи Яндекса. Тема о плагине не
знает, плагин о теме — тоже, и так остаётся.

| | Тема | Плагин |
|---|---|---|
| Формы | лид-формы `#hero-form`, `#signup` (`fs-lms-theme/inc/Forms.php`) | заявка `/apply/` (`inc/Modules/SmartCaptcha/`) |
| Ключи | опции `fs_lms_theme_captcha_site_key` / `_server_key`, «Настройки → Формы» | опция `fs_lms_smart_captcha` или константы `FS_LMS_CAPTCHA_SITE_KEY` / `_SERVER_KEY`; тумблер модуля на дашборде + секция в «Конфигурации» |
| Виджет | видимый: `<div class="smart-captcha" data-sitekey>`, токен сам попадает в `smart-token` формы | невидимый: `smartCaptcha.render( …, { invisible: true } )`, токен — через `execute()` при отправке |
| Скрипт Яндекса | `captcha.js` на **всех** страницах, если заданы ключи (`Forms.php:147-152`, приоритет 25) | `captcha.js?render=onload&onload=__fsSmartCaptchaReady` только на `/apply/` (`SmartCaptchaModule.php:74-88`, приоритет 20) |
| Серверная проверка | `fs_lms_theme_captcha_validate()`, fail-open | `YandexSmartCaptchaProvider::validate()`, fail-open |

Серверная часть устроена одинаково: тему писали по образцу провайдера плагина. Разные —
только ключи и клиентский код. Остальной путь модуля в порядке: провайдер, конфиг,
сохранение ключей, `captcha.js`, `apply-form.js`.

**Дефекты.**
1. **Фатальная ошибка при включении модуля.** В `SmartCaptchaModule.php:61` метод
   `provideProvider( CaptchaProviderInterface $default )` объявлен без
   `use Inc\Contracts\CaptchaProviderInterface;`. Имя резолвится в
   `Inc\Modules\SmartCaptcha\CaptchaProviderInterface`. В итоге первый же
   `CaptchaProviderFactory::make()` падает с `TypeError`, и отправка кода подтверждения на
   `/apply/` отвечает 500 (`ApplicationCallbacks::ajaxSendOtpCode()`, `:262`). Проверено
   изолированным PHP-сниппетом.
2. **Возможный конфликт двух загрузчиков Яндекса.** На `/apply/` (а после 1.3 — и на
   `/sign-in/`) грузятся оба `captcha.js`: сначала плагина, потом темы. Если второй
   загрузчик переопределит `window.smartCaptcha`, невидимый виджет, отрисованный первым
   экземпляром, потеряется. Тогда `execute()` не вернёт токен, и отправка формы зависнет в
   ожидании. Не проверено — проверить в браузере после исправления дефекта 1.

**Что менять.**
1. Добавить импорт в `SmartCaptchaModule.php`.
2. На проде посмотреть, включён ли модуль (дашборд модулей). Если включён — отправка
   кода на `/apply/` уже сейчас падает, а в логе PHP есть `TypeError … provideProvider()`.
3. **Ключи.** Задать в модуле ту же пару, что у темы, или завести отдельную капчу в Yandex
   Cloud. Невидимость — параметр `render()` на клиенте, а не настройка капчи, поэтому одна
   пара подходит обоим виджетам, если домен совпадает. Где задать: секция «Настройка Yandex
   SmartCaptcha» во вкладке «Конфигурация» или константы в `wp-config.php`.
4. **Проверить дефект 2** на `/apply/` при заданных ключах и темы, и плагина. Если
   конфликт подтвердится, тема должна подключать свой скрипт только на страницах со своими
   формами. Это правка в `fs-lms-theme/inc/Forms.php:147-152` с той же проверкой паттернов
   в `post_content`, что уже есть в `fs_lms_theme_signup_button_url()`. Главная — особый
   случай: её формы зашиты в `templates/front-page.html`. Плагин чужой хендл не трогает.
5. Завести тест `tests/Unit/Modules/SmartCaptcha/SmartCaptchaModuleTest.php`:
   `provideProvider()` принимает `NullCaptchaProvider` и возвращает Yandex-провайдер.

**Проверка.**
- Модуль включён, ключи заданы, на `/apply/`:
  - код подтверждения отправляется;
  - виджета не видно;
  - в запросе уходит непустой `captcha_token`.
- Запрос с пустым `captcha_token` (curl) → «Проверка капчи не пройдена».
- Лид-форма темы на главной и на странице предмета по-прежнему отправляется.
- При выключенном модуле `/apply/` работает без капчи.

## 4. Скрытие плашки SmartCaptcha на `/apply/`

**Как сейчас.** Невидимый виджет рендерится без `hideShield` (`captcha.js:46-50`). Поэтому
Яндекс выводит плашку-щит `.SmartCaptcha-Shield` со ссылкой на политику обработки данных
`.SmartCaptcha-Shield-PrivacyLink`. Решено: скрываем жёстко.

Образца в теме нет. Она ставит видимый виджет `<div class="smart-captcha">` (чекбокс в
iframe), а плашка-щит бывает только у невидимого. В PHP, JS и CSS темы нет ни `hideShield`,
ни селекторов `Shield`/`PrivacyLink`.

**Что менять.**
1. **JS** — в `render()` (`src/js/frontend/services/captcha.js:46-50`) добавить
   `hideShield: true`. Это штатный параметр Яндекса.
2. **CSS-страховка** — в `src/scss/frontend/components/_apply-form.scss` правило
   `.SmartCaptcha-Shield-PrivacyLink { display: none !important; }`:
   - нужно на случай, если скрипт Яндекса проигнорирует параметр или выставит элементу
     инлайновый стиль;
   - `!important` — с комментарием-причиной «перебиваем инлайновые стили стороннего
     скрипта» (правило `src/scss/CLAUDE.md`);
   - селектор верхнего уровня, не вложенный в блок `.fs-apply-card`. Сначала проверить в
     DevTools, куда Яндекс вставляет плашку: обычно в конец `body` с фиксированным
     позиционированием, то есть вне формы. Если ссылка окажется внутри iframe, CSS до неё
     не дотянется — тогда остаётся только п. 1.

**Риск.** Условия Яндекса разрешают скрывать плашку только при условии, что пользователь
уведомлён об обработке данных SmartCaptcha. На `/apply/` такого текста нет
(`templates/frontend/apply-fields.php`).

**Проверка.**
- `npx gulp build`, `npm run lint:css`.
- Модуль включён, ключи заданы. На `/apply/` плашки не видно ни при загрузке, ни после
  `execute()`. Если элемент есть в DOM, у него `display: none`.
- Код подтверждения по-прежнему отправляется, в запросе непустой `captcha_token`.

## 1.1. Лимит неудачных входов

**Как сейчас.** На `wp_login_failed` плагин только пишет журнал
(`AuthLogController.php:52`, приоритет 10) и возвращает на форму
(`AuthPageController.php:52`, приоритет 20). В `RateLimitService` нет счётчика входов.
Общий `check()` (`:229`) увеличивает счётчик на каждом вызове. Для схемы «проверить
блокировку без инкремента, считать только неудачи» он не подходит.

**Ключ и порог.**
- **Счётчик один: IP + пользователь — 3 неудачи за 15 минут.** После третьей вход с этой
  пары закрыт до конца окна. По нему же выводится предупреждение о последней попытке.
  Двадцать учеников за одним IP блокируются независимо друг от друга: у каждого свой логин.
- **Лимита по одному IP нет** (решение выше). Перебор разных логинов с одного адреса
  сдерживает капча из 1.3.
- **Глобальный счётчик по логину без привязки к IP тоже не заводим.** Без капчи он
  позволяет боту заблокировать вход конкретному человеку, например администратору.
- **«Пользователь» = ID**, если введённые логин или email существуют
  (`Managers/Person/UserManager::findByLogin()` / `findByEmail()`). Иначе — нормализованная
  строка (`mb_strtolower` + `trim`). Без этого, чередуя логин и email одного аккаунта,
  можно удвоить число попыток. В ключ идёт хэш с `FS_LMS_HASH_SALT`, как у
  `ipKey()` / `emailKey()`.
- **IP берётся из `RequestContextProvider::requestContext()`**, который учитывает
  `fs_lms_trusted_proxies`. Не из сырого `REMOTE_ADDR`, как в `ApplicationCallbacks.php:245`.

**Что менять.**

1. **`RateLimitService`** — новые методы:
   - `isLoginLocked( ip, userKey ): bool` — без инкремента;
   - `registerLoginFailure( ip, userKey ): int` — возвращает остаток попыток;
   - `clearLoginFailures( ip, userKey )`;
   - `loginRetryAfter( ip, userKey ): int` — минуты до конца окна.

   Рядом с `check()` — приватный `peek()`. Константы: `LIMIT_LOGIN = 3`, окно
   `15 * MINUTE_IN_SECONDS`. Префикс `fs_lms_rl_login_` дописать в список ключей в
   докблоке.

   Транзиенты остаются внутри сервиса: исключение из правила `TransientManager` на него
   уже распространяется.

   `isTestEnv()` лимит входа **не отключает** — так же, как `allowPiiReveal()`. Тумблер
   тестового окружения хранится в опции и может остаться включённым на проде.
2. **Новый `Inc\Services\Security\LoginGuardService`** — вся логика входа:
   - `guard( $user, string $login, string $captchaToken, string $ip )` — для фильтра
     `authenticate`. Сначала проверка блокировки (`WP_Error( 'fs_lms_login_locked' )`),
     затем капча (1.3). Если обе пройдены — возвращает `$user` без изменений;
   - `onFailure( string $login, WP_Error $error )` — учитывает неудачу, кроме кодов
     `fs_lms_login_locked` и `fs_lms_login_captcha`. Заблокированная попытка не продлевает
     окно, а непройденная капча не тратит попытки человека;
   - `onSuccess( WP_User $user )` — сбрасывает счётчик;
   - `noticeFor( … )` — состояние для формы: `failed` / `last` / `locked` и минуты ожидания.
3. **Новый `Inc\Controllers\Person\LoginGuardController`.** Добавить в
   `Init::getServices()` рядом с `AuthPageController` (`inc/Init.php:158`). Только хуки:
   - `authenticate`, **приоритет 30**. Раньше нельзя: `wp_authenticate_username_password`
     (приоритет 20, `wp-includes/default-filters.php:503`) затирает любой `WP_Error`,
     пришедший до него. На приоритете 30 блокировка срабатывает и при верном пароле, а
     результат проверки пароля бот не видит;
   - `wp_login_failed`, **приоритет 15**: после журнала (10) и до редиректа формы (20,
     там `exit`). С WP 5.4 ядро передаёт `WP_Error` вторым аргументом, поэтому
     `accepted_args = 2`;
   - `wp_login` → `onSuccess`.
4. **`AuthPageController::redirectFailedLogin()`** принимает `WP_Error`, а флаг для URL
   берёт из `LoginGuardService::noticeFor()`: `login=failed|last|locked`, для `locked`
   добавляется `wait=N`. Параметры URL нужны только для отображения — решение о блокировке
   принимает сервер.
5. **Уведомления на форме.** Сейчас `templates/frontend/auth-page.php:11-12` читает
   `$_GET` сам. Чтение перенести в `AuthPageController::renderLoginPage()` через
   `Sanitizer`, а в шаблон передавать готовый текст:
   - `failed` — «Неверный логин или пароль.»;
   - `last` — «Неверный логин или пароль. Осталась одна попытка, после неё вход будет
     закрыт на 15 минут.»;
   - `locked` — «Слишком много неудачных попыток. Повторите вход через N мин.»

   Текст одинаков для существующих и несуществующих логинов.

**Риск.** Если хостинг стоит за обратным прокси, а `fs_lms_trusted_proxies` не настроен,
у всех посетителей будет один IP. Тогда счётчик пары фактически станет счётчиком по
логину, и бот тремя неверными паролями закроет человеку вход на 15 минут. Капча из 1.3
этого не допускает. Перед выкладкой открыть журнал входов на проде (Логи →
Аутентификация) и проверить, что у людей из разных мест разные IP.

**Проверка.**
- `RateLimitServiceTest`:
  - третья неудача закрывает пару;
  - четвёртая попытка с верным паролем тоже отклонена;
  - другой логин с того же IP не затронут;
  - по истечении окна пара снова открыта;
  - успешный вход сбрасывает счётчик.
- Новый `LoginGuardServiceTest`:
  - коды `locked` и `captcha` не учитываются;
  - логин и email одного пользователя дают один ключ;
  - после второй неудачи `noticeFor()` возвращает `last`.
- Вручную: две ошибки → предупреждение, третья → блокировка, через 15 минут вход снова
  открыт.

## 1.2. Логины не должны утекать гостям

**Как сейчас.** Ни на один из каналов ниже в плагине нет фильтров. `user_nicename` —
это `sanitize_title( login )` (`UserManager.php:152`), поэтому любой адрес автора
раскрывает логин.

**Что менять.** Логику вынести в новый `Inc\Services\Security\UserEnumerationGuard`.
Хуки — в контроллер из 1.1 или в отдельный `UserEnumerationController`, если тот
разрастётся.

1. **REST** — фильтр `rest_pre_dispatch`. Если маршрут начинается с `/wp/v2/users` и
   `! is_user_logged_in()`, вернуть `WP_Error( 'rest_user_cannot_view', …, 401 )`.
   - Проверка по маршруту закрывает и `?rest_route=/wp/v2/users`, и встраивание автора
     через `_embed` в `/wp/v2/posts`: оно идёт через тот же `dispatch()`.
   - Гейт — именно по факту входа, а не по праву `list_users`: редактор под учётками
     преподавателей обращается к `/wp/v2/users/me` и `?who=authors`.
2. **Архивы авторов** — `template_redirect`, **приоритет 1**. Если `is_author()` (это и
   `?author=N`, и `/author/slug/`) — отдать 404.
   - Приоритет ниже 10 обязателен: на 10 висит `redirect_canonical`, который раньше
     любого шаблона отдаёт логин в заголовке `Location`.
   - Страниц авторов в LMS нет, поэтому закрываем их для всех.
3. **Карта сайта ядра** — `wp_sitemaps_add_provider`: для провайдера `users` вернуть
   `false`. Иначе `wp-sitemap-users-1.xml` перечисляет адреса авторов.
4. **oEmbed** — `oembed_response_data`: убрать `author_url` и `author_name`.
5. **Сообщения нативной формы** — фильтр `login_errors`. Коды `invalid_username`,
   `invalid_email` и `incorrect_password` заменить одной фразой «Неверный логин или
   пароль». Сейчас бот, отправляющий POST прямо на `wp-login.php`, получает от ядра
   сообщение «пользователь не зарегистрирован», и через него тоже можно перебирать логины.
6. **Восстановление пароля.** Оно отключено осознанно, но только для GET:
   `redirectToCustomLogin()` уводит на `/sign-in/` лишь GET-запросы. POST на
   `wp-login.php?action=lostpassword` ядро обрабатывает (`wp-login.php:836-845` →
   `retrieve_password()`). Бот узнаёт, существует ли логин («There is no account with that
   username…»), и может рассылать живым пользователям письма сброса. Что сделать:
   - на `login_form_lostpassword`, `login_form_retrievepassword`, `login_form_rp` и
     `login_form_resetpass` — они срабатывают до обработки, `wp-login.php:571` — делать
     редирект на `/sign-in/` для любого метода;
   - фильтр `allow_password_reset` → `false`. Он закрывает и сброс через «Мой аккаунт»
     WooCommerce: плагин установлен и подменяет `lostpassword_url`, если страница
     аккаунта заведена;
   - убрать мёртвую ссылку «Забыли пароль?» из `templates/frontend/auth-page.php:43-45`,
     а вместе с ней `lost_pass_url` из `AuthPageController::renderLoginPage()` (`:71`).

**Вне минимального набора** (зафиксировать, сейчас не делать):
- пароли приложений (`wp_is_application_passwords_available`);
- двухфакторная аутентификация для администраторов;
- плагин `wp-file-manager` стоит в локальном окружении и исторически был источником RCE —
  на проде его быть не должно.

**Проверка.**
- `UserEnumerationGuardTest`:
  - гость на `/wp/v2/users` и `/wp/v2/users/1` получает 401;
  - залогиненный пользователь проходит;
  - остальные маршруты не затронуты.
- Вручную под гостем:
  - `/wp-json/wp/v2/users` → 401;
  - `/?author=1` → 404 без редиректа (`curl -I`);
  - в `/wp-sitemap.xml` нет users;
  - `curl -d "user_login=admin" "…/wp-login.php?action=lostpassword"` → 302 на
    `/sign-in/`, письмо не уходит.
- Под преподавателем в админке открывается редактор задания.

## 1.3. Невидимая SmartCaptcha на входе

**Как сейчас.** Модуль работает только на `/apply/`:
- ключ кладётся в `fs_lms_apply_vars` (`SmartCaptchaModule.php:55`);
- скрипт Яндекса грузится только на `PageRoutes::Apply` (`:77`);
- `captcha.js` берёт ключ только из `fs_lms_apply_vars`
  (`src/js/frontend/services/captcha.js:20-23`).

Параметр `invisible: true` уже задан (`captcha.js:48`), заново его заводить не нужно.
Плашку Яндекса об обработке данных скрывает пункт 4 — `render()` общий, поэтому на
`/sign-in/` она тоже не появится. Задача опирается на пункт 3: модуль должен быть
исправлен и включён.

**Что менять.**

1. **Ядро, данные формы.** В `FrontendAssets::localizations()`
   (`inc/Core/Assets/FrontendAssets.php:125-135`) добавить переменную `fs_lms_login_vars`
   на `PageRoutes::SignIn` с фильтром `fs_lms_login_vars` (по образцу `applyVars()`,
   `:145`). Ядро про капчу не знает — `captcha_key` дописывает модуль.
2. **Модуль.**
   - В `SmartCaptchaModule::register()` добавить
     `add_filter( 'fs_lms_login_vars', addCaptchaKey )`.
   - В `enqueueCaptchaScript()` условие расширить до `Apply || SignIn`.
   - Упоминание «/lms/apply» дополнить формой входа: докблоки модуля и
     `SmartCaptchaConfig`, описание модуля на дашборде
     (`SmartCaptchaSettingsController.php:69`), тексты секции настроек
     (`templates/settings-section.php`), строка модуля в `.docs/basic_doc.md:1486`.
3. **Шаблон.** В форму `templates/frontend/auth-page.php` добавить слот
   `<div id="fs-captcha-slot">` и `<input type="hidden" name="captcha_token">`.
4. **JS.**
   - `captcha.js` берёт ключ из `fs_lms_apply_vars` или `fs_lms_login_vars` через
     приватный `siteKey()`; на нём строятся `isCaptchaEnabled()` и `initCaptcha()`.
   - Новый `src/js/frontend/services/login-form.js` с `initLoginForm()` (гард по
     `#loginform` и `fs_lms_login_vars`), подключить в `frontend.js`.
   - Отправка формы при включённой капче и отсутствии токена: `preventDefault` →
     кнопка блокируется → `getCaptchaToken()` → токен пишется в `captcha_token` →
     `form.requestSubmit( button )` с флагом, чтобы в POST ушёл `wp-submit`.
   - На `captcha-dismissed` — разблокировать кнопку и вызвать `resetCaptcha()`.
5. **Сервер** — `LoginGuardService::guard()` из 1.1, после проверки блокировки:
   - капча обязательна только при `CaptchaService::isConfigured()` (заданы оба ключа).
     Иначе при заданном серверном и пустом клиентском ключе виджет не отрисуется, и не
     сможет войти никто;
   - капчу требовать на любом POST на `wp-login.php` с полем `log`, а не только при
     маркере `fs_lms_login`: бот маркер не пришлёт;
   - токен читает контроллер (`Sanitizer`) и передаёт в сервис; IP — тот же, что в 1.1;
   - при неуспехе — `WP_Error( 'fs_lms_login_captcha' )`, форма показывает
     `login=captcha`: «Не удалось пройти проверку, попробуйте ещё раз»;
   - при `isTestEnv()` капча пропускается, как в `ApplicationCallbacks.php:260`.
6. **Порядок в `guard()`:** блокировка → капча → результат проверки пароля. Непройденная
   капча не доходит до счётчика из 1.1, поэтому бот, не решивший капчу, не может
   заблокировать вход живому человеку.

**Риски.**
- **Скрипт Яндекса не загрузился** (блокировщик, сеть). Токен пустой, а
  `YandexSmartCaptchaProvider::validate()` на пустой токен возвращает `false` (`:50-52`).
  Fail-open срабатывает только при сбое серверного запроса (`:63-66`), так что человек с
  блокировщиком не войдёт. Как смягчить:
  - JS показывает «Проверка безопасности не загрузилась — отключите блокировщик и
    обновите страницу»;
  - аварийный выключатель — константа `FS_LMS_SMART_CAPTCHA = false` в `wp-config.php`
    (уже поддержана в `SmartCaptchaConfig::toggleConstant()`).
- **Два загрузчика Яндекса.** Тема грузит свой `captcha.js` и на `/sign-in/`
  (`clean-page.php` вызывает `wp_head`/`wp_footer`). Проверка и исправление — те же, что в
  п. 3, дефект 2.
- **Форма входа WooCommerce на «Мой аккаунт».** Она вызывает `wp_signon()` в обход
  `wp-login.php`. Лимит из 1.1 на неё действует, а капча — нет. Проверить, открыта ли эта
  форма на проде. Если открыта, либо закрыть её (вход только через `/sign-in/`), либо
  требовать капчу на любом интерактивном `authenticate` — кроме REST, XML-RPC и WP-CLI.

**Проверка.**
- `LoginGuardServiceTest`:
  - без токена при настроенной капче → `fs_lms_login_captcha`;
  - без токена при ненастроенной капче вход проходит;
  - заблокированная пара отклоняется до проверки капчи.
- Вручную (модуль включён, ключи заданы):
  - вход с формы проходит без видимого виджета;
  - `curl -d "log=…&pwd=…" …/wp-login.php` без токена → отказ, счётчик не растёт;
  - при выключенном модуле вход работает как раньше.

## 2. Ширина страниц статей и заданий — 1160 вместо 1200

**Как сейчас.** Шапка и страницы темы ограничены
`layout.contentSize` / `wideSize: 75rem` = 1200 px
(`themes/fs-lms-theme/theme.json:121-122`). Публичные страницы плагина ограничены
собственным токеном `$max-width: t.rem(1160)` (`src/scss/frontend/_variables.scss:113`).
1160 — ширина раннего мокапа (`design-mockup/project/Главная - мокап.dc.html`). Тема с тех
пор перешла на 1200, а токен плагина остался прежним. На широком экране контент плагина
уже шапки на 20 px с каждой стороны.

Токен задаёт ширину не только статей и заданий, а всех публичных страниц плагина:
- задание `/{key}/trainer/{номер}/` — `.fs-page-shell` (`_layout.scss:12`);
- статья — `.fs-article-page .shell` (`article/_shell.scss:11`);
- тренажёр и каталог учебника — `.shell` (`all-tasks/_shell.scss:15`) и липкая панель
  (`all-tasks/_toolbar.scss:26`);
- разделы лендинга — `.fs-subject-section` (`_subject-page.scss:12`);
- карусель — `_carousel.scss:5`, `:23`;
- легаси-плеер — `_lesson-player.scss:8`.

**Что менять.**

1. `$max-width: t.rem(1200)` — одна строка, новый токен не нужен.
2. Производная `$subject-card-width` (`_variables.scss:118`) пересчитается сама:
   268.67 → 282 px. Затронутые сетки:
   - **каталог учебника с сайдбаром** (`_articles-page.scss:49`):
     3 × 282 + 2 × 16 = 878 = 1200 − 300 − 22. Три колонки, как и было.
   - **сетка курсов без сайдбара** (`_subject-page.scss:29`): 4 × 282 + 3 × 24 = 1200.
     Ровно четыре колонки без запаса (раньше запас был 13 px). Проверить, что дробные rem
     не переносят четвёртую колонку на новую строку. Если переносят, `minmax` не вводить
     (см. комментарий в файле), а уменьшить зазор до существующего `$spacing-lg`.
   - **слайд карусели** (`_carousel.scss:69`): 298 px, в полосу по-прежнему входят
     четыре слайда.
3. Боковые отступы (`fs-page-pad`, `_mixins.scss:191-193`: 32 px, на мобильных 16 px) не
   трогаем. У самой темы отступы шапки (`patterns/header-nav.php:66`, 1.5rem) и контента
   (root padding 2.5 / 2 / 1rem) различаются. При ширине окна от 1248 px всё центрируется
   по 1200, так что для выравнивания достаточно поменять один токен.

**Проверка.**
- `npx gulp styles:frontend` и `npm run lint:css`.
- В браузере на 1440 px левый край контента совпадает с логотипом шапки на страницах
  задания, статьи, тренажёра, учебника и курсов предмета.
- На 1024 и 390 px макет не ломается: сетка курсов, карусель, липкий сайдбар статьи.
