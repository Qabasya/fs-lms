# Публичные экзамены: этапы реализации

Источник требований — `.docs/public-exam-feature/SPEC.md` (приоритет), решения — `DECISIONS.md`. Ветка `public-exams`. Слои кода следуют `CLAUDE.md`. Мокап — иллюстрация, не исходник.

Каждый этап самостоятельный: у него есть результат, который можно проверить отдельно, не дожидаясь следующих. Этап считается закрытым, только когда пройдены его проверки (PHPUnit, `npm run ci`, ручная/e2e-проверка), а не когда нарисован UI. Этапы идут по порядку; зависимости указаны.

## Вехи (что можно выпускать отдельно)

| Веха | Этапы | Что получают пользователи |
|---|---|---|
| **M1. Запись** | 0–5 | Преподаватель назначает экзамен, ученики записываются, родитель смотрит. Экзамен ещё не сдаётся |
| **M2. Сдача и результаты** | 6–10 | Сдача на существующей станции, неявка, проведение, проверка и массовое утверждение, «Результаты», уведомления, статистика |
| **M3. Гости и школы** | 11–12 | Гостевая запись/вход/результат, школьные отчёты. **Начинается после согласования формы гостя** |
| **Выпуск** | 13 | Нагрузочная и визуальная приёмка, retention, документация |

---

## Этап 0. Подготовка и исправления
Зависимости: нет. Результат: исправленный конструктор и контракт форматов, без видимой новой фичи.

- [ ] 0.1 Число позиций КЕГЭ в конструкторе работ берётся из формата (27), а не из `wp_count_terms` таксономии; проверка полноты `EgeCompletenessChecker` читает тот же источник (SPEC §13). Дополнительные реальные задачи старых работ не обрезать молча.
- [ ] 0.2 Отступы `fs-field__label` в админке (без глобального побочного эффекта на другие формы).
- [ ] 0.3 Контракт форматов экзамена в ядре: фильтр/интерфейс, через который ядро получает от модуля `EgeComputer` число единиц, максимум, шкалу, длительность, направление (ЕГЭ/ОГЭ). Ядро не ссылается на классы модуля (SPEC §0).
- [ ] 0.4 Capabilities `ManageExams`, `ManageExamGuests`, `ShareExamResults` в `Capability`; выдача ролям: преподаватель (scope своих предметов), методист и администратор (глобально); Office/Market — нет. Миграция ролей по `db-migrations`.
- [ ] 0.5 Энумы: статусы проведения/сеанса/записи/участия, ключи опций и транзиентов, `TableName` для новых таблиц.

Проверка: PHPUnit на 0.1/0.3/0.4; в конструкторе работы КЕГЭ предлагает ровно 27 позиций при любом числе терминов; существующие тесты `EgeCompletenessChecker` и конструктора зелёные.

## Этап 1. Аудитория записи и права на предмет
Зависимости: 0. Результат: сервис «кому доступен экзамен», проверяемый без UI записи. Направление ЕГЭ/ОГЭ уже заложено в предметах (`inf_ege`, `inf_oge`), новых полей и миграций нет.

- [ ] 1.1 `ExamAudienceResolver`: активные ученики, зачисленные в группы предмета проведения (`groups.subject_key`); родители этих детей; пересчёт при зачислении/выбытии/смене группы.
- [ ] 1.2 Серверная проверка прав на предмет проведения для преподавателя (`TeacherSubjectsService` с fallback на все предметы не использовать); методист и администратор — глобально.
- [ ] 1.3 Валидация: варианты проведения принадлежат его предмету.

Проверка: PHPUnit на резолвер (ученик в двух группах предмета, отчисленный, группа другого предмета, предмет ЕГЭ и ОГЭ не смешиваются); WP-CLI-команда выводит аудиторию для предмета.

## Этап 2. Схема БД и домен проведений
Зависимости: 0. Результат: таблицы, DTO, репозитории; без UI.

- [ ] 2.1 DDL: `exam_events`, `exam_sessions`, `exam_participants`, `exam_participations`, `exam_registrations` (с `active_slot`), `exam_sources`, `exam_access_tokens`, `exam_guest_sessions`, `exam_reports`, `exam_report_members`, `exam_events_outbox`, `exam_operation_keys` (SPEC §11). Таблицы гостей/отчётов создаются сразу, наполняются в M3.
- [ ] 2.2 Расширение `assessment_attempts`: `exam_participation_id`, `exam_registration_id`, `student_person_id` nullable только для новых гостевых попыток; уникальность официальной попытки по участию.
- [ ] 2.3 DTO, Repositories (WPDB), `Clock`-зависимый сервисный слой по `ClockInterface`; время хранится в UTC-модели новых таблиц с адаптером к старым.
- [ ] 2.4 `ExamEventService`: создать/изменить/опубликовать/отменить проведение; сеансы с валидацией дат, вместимости (`RoomDTO.seats` — верхний предел).
- [ ] 2.5 Миграция по `db-migrations`: DDL повторяемый, без дропа core-таблиц (сброс `fs_lms_schema_version` запрещён).

Проверка: PHPUnit (сервисы, валидации); integration-тесты репозиториев на реальной MariaDB; миграция применяется дважды без потерь.

## Этап 3. Сервис записи и защита от гонок (без UI)
Зависимости: 2. Результат: `ExamRegistrationService` + стенд параллельных запросов.

- [ ] 3.1 register/change/cancel по SPEC §4: условный `UPDATE occupied_count < capacity`, `UNIQUE(participation_id, active_slot)`, единый порядок блокировок, повтор на deadlock 1213/1205, idempotency key.
- [ ] 3.2 Самоотмена и перенос до начала своего сеанса; отмена сотрудником с причиной; история броней; перенос с сохранением старой брони при неуспехе.
- [ ] 3.3 Правила: одна активная бронь на участие, пересечение с другими экзаменами, ограничение окном записи, коды `full/registration_closed/conflict/stale_version`.
- [ ] 3.4 Стенд нагрузки (скрипт + WP-CLI): N параллельных процессов с двумя+ соединениями к реальной MariaDB.

Проверка (критерии SPEC §16: 1–4, 6, 32–35): 100 параллельных записей на 20 мест → ровно 20; повтор запроса не дублирует; неуспешный перенос сохраняет старую бронь. FakeWpdb не считается проверкой гонок.

## Этап 4. Календарь преподавателя «Назначить экзамен»
Зависимости: 1, 2. Результат: преподаватель создаёт и публикует проведение.

- [ ] 4.1 Пункт меню «Мои экзамены» у преподавателя: «Проведение экзамена / Статистика / Назначить экзамен / Результаты» (экраны-заглушки до своих этапов).
- [ ] 4.2 Календарь по месяцам на адаптере к календарю КТП (предмет вместо группы, вариант вместо темы, сеанс вместо урока); добавление сеанса кнопкой и перетаскиванием варианта в одну форму; мобильная альтернатива без drag/drop.
- [ ] 4.3 Форма сеанса: время, вариант, кабинет (обязателен), вместимость ≤ мест кабинета, ответственный.
- [ ] 4.4 Кабинет занят ровно `[начало, плановый конец]`; двусторонняя проверка экзамен ↔ экзамен и экзамен ↔ занятие; сериализация назначения. Предупреждение о позднем старте после планового конца — только преподавателю.
- [ ] 4.5 «Настройки проведения»: название, период (любой, через выходные и месяцы), открытие/закрытие записи, основной вариант; публикация после корректного сеанса.
- [ ] 4.6 События экзаменов в расписании преподавателя и на «Главной»; клик → «Проведение экзамена».

Проверка: PHPUnit на конфликты кабинета (в т. ч. запись занятия после экзамена и наоборот); e2e (headless CDP): создать проведение на 4 и на 10 дней, через границу месяцев, на телефонной ширине добавить сеанс без drag/drop.

## Этап 5. «Мои экзамены» ученика и родителя: запись
Зависимости: 1, 3, 4. Результат: ученик записывается, родитель смотрит. Сдача пока не открыта.

- [ ] 5.1 Пункт меню «Мои экзамены» для ученика и родителя — виден всегда, пустое состояние; переключатель ребёнка.
- [ ] 5.2 Плитки и карточка по образцу «Мои курсы» (`sc-tabs`, `prof-card.sc-hero`): все состояния SPEC §5 — не открыта запись, открыта, мест нет, закрыта, записан (серая «Приступить»), вход открыт (синяя), отменён, неявка, проведение отменено.
- [ ] 5.3 «Записаться» → плитки сеансов (дата, день недели, время, места) → «Подтвердить запись»; при `full` плитки обновляются, ничего не бронируется; «Отмена выбора» возвращает действующую запись; самоотмена и смена с подтверждением.
- [ ] 5.4 Родитель: та же проекция без изменяющих действий, запрет на сервере (прямой POST отклоняется).
- [ ] 5.5 События экзамена в расписании ученика/родителя; клик у ученика → карточка со стартом.
- [ ] 5.6 Включение ОГЭ: те же экраны и правила для проведений ОГЭ (плитка — первичные и отметка).

Проверка: PHPUnit на Callbacks (запись/отмена/родитель); e2e: ученик группы предмета ЕГЭ видит только проведения этого предмета, ученик ОГЭ — свои; двое одновременно на последнее место; родитель не может записать.

**Конец M1: можно выпускать запись без сдачи.**

## Этап 6. Сдача вне курса: попытки, неявка, блокировка
Зависимости: 3, 5. Результат: ученик реально проходит экзамен на существующей станции.

- [ ] 6.1 `AttemptContext` для student (guest позже): старт/продолжение/сохранение/сдача идут через единый контекст; допуск проверяется на сервере в момент старта (`начало ≤ now < плановый конец`).
- [ ] 6.2 Личный дедлайн = фактический старт + длительность + продления; плановый конец закрывает вход и определяет неявку, но не прерывает начатое; автоистечение по дедлайну без потери автосохранений.
- [ ] 6.3 Неявка: фоновая и ленивая проверка на `planned_end`; идемпотентна; согласована со стартом/отменой блокировкой участия; бронь → `missed`, снова доступна запись.
- [ ] 6.4 `ExamLockService` для попыток вне курса: блокировка контента на время попытки, снятие при любом терминальном исходе.
- [ ] 6.5 Кнопка «Приступить» открывает существующую станцию КЕГЭ/ОГЭ; «Продолжить» с остатком времени.
- [ ] 6.6 Убрать добавление экзамена-станции в шаг курса; Control остаётся шагом курса и не меняется.
- [ ] 6.7 Исключить экзаменационные попытки из журнала группы, «Мои работы», learner-grades и старых сводок (SPEC §11).

Проверка (SPEC §16: 5, 6, 7, 31): границы 09:59 / 10:00 / 13:54 (дедлайн 17:49) / 13:55; одновременные start/missed/cancel; старый Control без регрессий; экзамен не виден в журнале; e2e: полный проход ЕГЭ на станции.

## Этап 7. Общий renderer задач и «Результаты» ученика
Зависимости: 6. Результат: разбор экзамена у ученика/родителя.

- [ ] 7.1 Общий renderer задач из `work-review.js` с режимами manage/read_only; «Работы» используют его же (без регрессий).
- [ ] 7.2 Статусы correct/incorrect/unanswered/partial/pending; устойчивые якоря единиц оценивания (не индекс строки).
- [ ] 7.3 Баллы: КЕГЭ 27 единиц / 29 первичных / 100, №26–27 по 2 (18→72, 22→83); ОГЭ — первичные из 21 и отметка; повторы и составные задачи по `ScoringUnits`.
- [ ] 7.4 Экран «Результаты» (полноэкранный, не модалка) и перечень заданий в карточке с бейджами; клик → экран с прокруткой к заданию.
- [ ] 7.5 Reveal-политика: ученик/родитель до утверждения не получают баллы, эталоны, решения ни в HTML, ни в JSON, ни в файлах, ни в уведомлениях; старый `AttemptGraded`-подписчик не обходит утверждение.

Проверка (SPEC §16: 15, 19, 20): тесты на утечку (curl/JSON до approve); баллы КЕГЭ/ОГЭ; визуальная сверка с «Работами»; таблицы/код/файлы ОГЭ не теряются.

## Этап 8. «Проведение экзамена» и утверждение
Зависимости: 6, 7. Результат: преподаватель ведёт сеанс и утверждает работы.

- [ ] 8.1 Таблица сеанса: участник, статус (не начат/в процессе/сдал/неявка), старт, дедлайн, остаток, статус результата; автообновление.
- [ ] 8.2 Действия: отмена не начатой записи с причиной, назначение другого сеанса, продление активной попытки с причиной и автором, отметка «Пришёл» (необязательная, неявку не отменяет), открыть работу.
- [ ] 8.3 Экран проверки: существующий `work-review` в manage-режиме, ручная часть ОГЭ, pending без фиктивного итога.
- [ ] 8.4 Утверждение: одиночное на экране проверки; **массовое**: «Утвердить работы» → выбор → «Утвердить выбранные (N)» / «Утвердить все» / «Отмена»; только готовые работы; частичный успех с отчётом.
- [ ] 8.5 Исправление результата с причиной, версией, журналом старых/новых значений.
- [ ] 8.6 Раздел «Результаты»: фильтры проведения/сеанса/статуса, очередь проверки.
- [ ] 8.7 Печать списка участников и CSV — только при `ManageLmsPlatform` + `ExportPII`, без контактов; защита от formula-injection.

Проверка (SPEC §16: 6, 8, 16, 27, 29): продление и отмена; массовое утверждение на 50 работах; одновременное исправление двумя проверяющими; CSV с `=…`, `+…`, `@…`.

## Этап 9. Уведомления в кабинете
Зависимости: 3, 6, 8. Результат: все события SPEC §10 в ленте ученика/родителя/преподавателя.

- [ ] 9.1 Типы `NotificationType` и серверные тексты для всех событий §10; email и мессенджеры не добавляются.
- [ ] 9.2 Outbox: событие пишется в той же транзакции, worker после commit создаёт уведомления с уникальным ключом event/version/recipient/type.
- [ ] 9.3 Напоминания «завтра» (18:00 накануне) и «скоро начало» (за 60 минут): повторная проверка актуальности брони, снятие при отмене/переносе, пропуск просроченных при поздней записи.
- [ ] 9.4 Регулярный серверный запуск раз в минуту (не WP-Cron по посещаемости) с lock от параллелизма; инструкция в handoff.
- [ ] 9.5 Массовое утверждение не дублирует «Работа утверждена»; «Результат исправлен» с причиной.

Проверка (SPEC §16: 23): перенос снимает старые напоминания; повтор worker не дублирует; недоставка/сбой worker не открывает просроченный старт.

## Этап 10. Статистика
Зависимости: 8. Результат: экран «Статистика» (SPEC §7).

- [ ] 10.1 Фильтры предмет/проведение/сеанс/ученики; KPI: записано, начали, сдали, не явились, ожидают проверки, средние баллы с размером выборки.
- [ ] 10.2 По заданиям: доли полного/частичного/ошибок/пропусков/pending; №26–27 по 2; шкалы разных форматов не смешиваются; отменённые брони и архивные попытки не искажают.

Проверка: PHPUnit на агрегаты на фикстурах; сверка с ручным подсчётом.

**Конец M2: полный цикл для учеников центра.**

## Этап 11. Гости *(начинается после согласования формы и правил брони гостя)*
Зависимости: 2, 6, 7, 8. Блокер: решение по форме гостя и по занятию места гостевой заявкой (SPEC §6, DECISIONS).

- [ ] 11.1 Участник-гость (`exam_participants`, nullable Person), дедупликация и кандидаты на дубль, связывание с Person; автоматического зачисления нет.
- [ ] 11.2 Публичная страница проведения и форма (тема сайта, SmartCaptcha, лимиты с учётом общего IP); согласия тем же механизмом, что в лид-форме (`ConsentService`), несовершеннолетние по поведению лид-формы.
- [ ] 11.3 Правило брони гостя (место сразу / после проверки) — по итогам согласования.
- [ ] 11.4 «Добавить гостя на месте» в сеансе.
- [ ] 11.5 Ссылка на вход: кнопка «Выдать ссылку» копирует адрес, ключ в хеше, обмен на HttpOnly-сессию, URL без ключа; «Не получается войти»; экран «Ссылка недействительна».
- [ ] 11.6 `AttemptContext` для гостя; результат сразу после сдачи на странице сайта (шапка, сайдбар, CTA), ручная часть ОГЭ — pending.
- [ ] 11.7 Кнопка «Завершить сеанс» на конечном экране: отзыв сессии, no-store, сессия не переживает закрытие браузера.
- [ ] 11.8 Личная ссылка результата: выдача, отзыв, перевыпуск.

Проверка (SPEC §16: 12–14, 30): гость сдаёт и видит разбор, не попадая в списки учеников; по ФИО/телефону чужую запись получить нельзя; «Назад» после «Завершить сеанс» не показывает разбор; гость не отменяет и не меняет сеанс прямым POST.

## Этап 12. Источники школ и школьные отчёты
Зависимости: 8, 11 (для гостей; для учеников центра можно раньше). Результат: отчёт школьному преподавателю по ссылке.

- [ ] 12.1 Источники приглашения (`exam_sources`): школа, школьный преподаватель, стабильный ID; подсказки школ из существующего справочника; приглашение подставляет источник в форму.
- [ ] 12.2 Отчёт: именованная фиксированная выборка участий (гости и ученики центра; для центра согласие на передачу не требуется, для гостей — только согласившиеся), срок 90 дней по умолчанию, отзыв, перевыпуск.
- [ ] 12.3 Страница отчёта на сайте: таблица результатов, под ней раскрываемый read-only разбор выбранного участника (навигация по заданиям → задания); проверка членства в отчёте на каждом переходе.
- [ ] 12.4 Без контактов, личных ссылок, CSV и действий от имени участника; noindex/no-store/Referrer-Policy.

Проверка (SPEC §16: 17, 18, 26): подмена attempt_id и токена чужого назначения → отказ без утечки; новый гость той же школы в отчёт не попадает; ученик центра включается без гостевого согласия.

**Конец M3.**

## Этап 13. Эксплуатация и приёмка
Зависимости: все предыдущие.

- [ ] 13.1 Нагрузочная приёмка (SPEC §16: 32–37) на реальной MariaDB и PHP-FPM: 100 параллельных записей на 20 мест, несколько сеансов, повтор одного участника, 50 участников одного сеанса (burst-старт, автосохранение, одновременная сдача), граница неявки для 50. Протокол с цифрами в отчёт.
- [ ] 13.2 Защита неизменяемости варианта: фиксация состава/весов/шкалы при первом старте и guard на всех путях правки (админка, inline, импорт, удаление файлов/предмета) (SPEC §12); тесты на каждый путь.
- [ ] 13.3 Retention и удаление гостей (365 дней по умолчанию, настраиваемо): отзыв доступов, обезличивание, не трогая действующий Person.
- [ ] 13.4 Визуальная приёмка desktop/mobile рядом с «Работами», КТП, публичным сайтом; проверка существующего плеера КЕГЭ/ОГЭ с телефона и предупреждение до старта.
- [ ] 13.5 Полный `npm run ci`, сборка бандлов, PHPUnit; e2e-обход через headless CDP.
- [ ] 13.6 Документация: `ReleaseHistory_1.0.x.md`, инструкция по серверному cron, handoff.

## Порядок и параллельность

```
0 → 1 ┐
0 → 2 → 3 ┬→ 4 ┬→ 5 (M1)
         │    └→ 6 → 7 → 8 → 9, 10 (M2)
                         ↘ 11 → 12 (M3) → 13
```

Этапы 1 и 2 независимы друг от друга и могут идти параллельно после 0. Этап 4 можно начинать до завершения 3 (нужен только домен из 2), а этап 7 — частично параллельно с 6 (renderer не зависит от попыток).
