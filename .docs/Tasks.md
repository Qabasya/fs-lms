# Техническое обслуживание FS LMS — план реализации

Дата: 2026-11-07. Статус: согласованное поведение, реализация не начата.

## 1. Назначение и границы

Один режим: **«Техническое обслуживание»**. Пользователи просматривают данные, администраторы продолжают обычную работу. Нужен для массового редактирования заданий, перенастройки платежей, пересчёта баллов, импорта данных серверными командами.

Полное закрытие сайта не входит в эту фичу: выполняется отдельно средствами WordPress/сервера. Плагин не создаёт `.maintenance` и не выключает обслуживание автоматически.

Гарантия: пользовательские изменения и автоматические изменения доменных данных FS LMS остановлены. Изменять их могут администраторы и явно запущенные команды обслуживания. Это не заморозка всей БД: сессии WordPress, технические кеши, аудит, другие плагины и внешние процессы требуют отдельного контроля. Для переноса БД нужна серверная остановка всех источников записи.

### Согласованное поведение

| Область | Во время обслуживания |
|---|---|
| Публичные лендинги, задания, статьи | Доступны для просмотра |
| ЛК с действующей сессией | Только чтение для всех обычных ролей, включая сотрудников |
| Новые входы | Обычным пользователям запрещены; администраторам доступны |
| Администраторы | Обычный доступ к сайту, админке и операциям записи |
| Формы, ответы, загрузки, самозапись, изменения профиля | Запрещены обычным пользователям на сервере |
| Оплаты | Новые запрещены; ранее начатые требуют безопасной сверки |
| Почта FS LMS | Не отправляется, в том числе после действий администратора |
| Автоматические задачи FS LMS | Приостановлены без удаления расписаний и очередей |
| Внешние демоны | Интеграции приостановлены; фактическая остановка процесса требует поддержки демона/сервера |
| Ручные WP-CLI и серверные операции | Доступны; почта и автоматическая доставка интеграций остаются выключены |

Исключение администратора проверять по **`Capability::Admin` (`manage_options`)**. Не по имени роли и не по более широкому `ManageLmsPlatform`: последнее даёт доступ сотрудникам, которые не должны обходить обслуживание. Исключение не выдаёт новых прав: все существующие nonce, capability и доменные проверки сохраняются.

### Задачи

- [ ] Составить полную таблицу точек входа: AJAX core/модулей, REST, обычные POST/admin-post, WooCommerce checkout и Store API, webhooks, cron, CLI, shutdown-доставка, внешние демоны.
- [ ] Для каждой операции указать: чистое чтение / пользовательская запись / автоматическая запись / ручная административная операция / внешнее подтверждение оплаты.
- [ ] Проверить чтение с побочными эффектами: presence, отметки просмотра, прочитанность уведомлений, прогресс видео, ленивое истечение попыток и броней, no-show, создание записей при первом открытии ЛК. В частности проверить `ExamAttemptService` и `LearnerExamsService`.
- [ ] Определить реальные источники отправки почты, включая вызовы в обход `EmailService`, WooCommerce и очереди.
- [ ] Установить, где живёт код демонов, как они повторяют 503 и можно ли подтвердить паузу. Отсутствие такого протокола обозначить явно.
- [ ] Зафиксировать контракт ошибки `maintenance_active`, HTTP 503 и понятный текст; безопасные чтения сохраняют свои обычные ответы.

**Проверка:** у каждой найденной точки записи есть способ блокировки либо явное исключение. Новая неизвестная операция FS LMS не должна автоматически становиться разрешённым чтением.

**Ограничения:** не определять безопасность по GET/POST, префиксу `get` или признаку `is_admin()`; не блокировать весь WordPress и все сторонние API.

## 3. Фаза 1 — состояние и единая политика

- [ ] Добавить состояние в существующую конфигурацию: включено, время изменения, инициатор. Использовать `PluginConfigRepository`, не читать/писать опции из контроллеров.
- [ ] Добавить метод чтения состояния в `PluginConfig` и единый DI-сервис политики обслуживания в существующем сервисном слое. Имена новых методов зафиксировать при реализации; не считать их уже существующими API.
- [ ] По умолчанию обслуживание выключено; существующие установки работают без обязательного ручного перенастроения.
- [ ] Все переключения UI/CLI проводить через одну операцию: изменение состояния, аудит, обновление кеша состояния. Повторное включение/выключение идемпотентно.
- [ ] Не добавлять независимый флаг в модульные опции. Модули используют общую политику, ядро не перечисляет их внутренние константы.
- [ ] Не кешировать состояние надолго в воркере; повторно проверять перед каждым пакетом работы и при переходе к записи.
- [ ] Сохранить обычные проверки прав для администратора, не делать глобальный CLI-bypass по HTTP-параметру.

**Образцы:** `PluginConfigRepository::save()`, `PluginConfig`, регистрация сервисов в `Inc\Init::getServices()`.

**Проверка:** unit-тесты выключенного/включённого состояния, административного исключения, частичного сохранения, повторного переключения и чтения состояния новым запросом.

**Ограничения:** без новой таблицы, если достаточно существующей конфигурации; новые ключи `wp_options` — только через `OptionName`; не вводить собственный контейнер или статический singleton.

## 4. Фаза 2 — серверная блокировка пользовательских изменений

- [ ] Встроить общую проверку до выполнения обработчиков FS LMS. Использовать явный перечень проверенных операций чтения, включая POST/AJAX чтения; для мутирующих обходных транспортов добавить эквивалентную проверку.
- [ ] Закрыть изменения ученикам, родителям, преподавателям и другим неадминистративным ролям. Сохранить чтение с существующими проверками доступа к данным.
- [ ] Охватить отправку ответов, старт/завершение попыток, автосохранение, посещаемость, сообщения, загрузки, уведомления, домашнюю раскладку, профиль, согласия, заявки, OTP, самозапись и гостевые экзамены.
- [ ] Устранить доменные записи в разрешённых чтениях: показывать вычисленное состояние без сохранения либо откладывать изменение до возобновления задач. Не менять доступ к закрытым данным из-за отключения побочных записей.
- [ ] Разрешить безопасный выход из учётной записи. Истечение сессии не продлевать искусственно.
- [ ] Для запрета отвечать 503 с `maintenance_active`; существующий JS должен отображать сообщение без циклических повторов и без потери введённого текста в открытой вкладке.
- [ ] Проверять состояние не только в начале долгой операции, но и перед её атомарной записью. Определить барьер для уже выполняющихся мутирующих запросов при включении режима.

**Образцы:** `AjaxController`, `Authorizer`, `AjaxResponse`, модульные REST-контроллеры и инвентаризация фазы 0. AJAX-ответы — через существующий транспорт; REST — по контракту REST.

**Проверка:** при активном режиме реальные запросы обычных ролей не меняют доменные строки, разрешённые чтения работают; администратор редактирует задания и сохраняет настройки. Проверить запрос из вкладки, открытой до включения, GET с побочной записью и POST чтения.

**Ограничения:** отключённая кнопка не является защитой; не перехватывать произвольный SQL и не вводить глобальный запрет `update_option()`.

## 5. Фаза 3 — новые входы

- [ ] Добавить проверку обслуживания в существующий auth-поток после проверки учётных данных. Исключение администратора определять по проверенному `WP_User`, не по присланному логину.
- [ ] Запретить новые пользовательские входы на всех обнаруженных путях аутентификации, включая альтернативные API, если они включены. Действующие сессии сохранить.
- [ ] Добавить уведомление обслуживания в `LoginNotice` и корректный переход на `/sign-in/`.
- [ ] Отказ обслуживания не увеличивает счётчик неверного пароля и не раскрывает существование/роль пользователя. Неверные пароли сохраняют существующее безопасное поведение.
- [ ] Проверить административный вход при остановленном cron и недоступной/перенастраиваемой капче. Предусмотреть узкий безопасный путь восстановления через существующую защиту/CLI; не отключать защиту всех администраторов автоматически.

**Образцы:** `LoginGuardController`, `LoginGuardService`, `AuthPageController`, `.docs/LOGIN-SECURITY.md`.

**Проверка:** обычный пользователь с верным паролем не входит; существующая сессия читает ЛК; администратор входит; лимиты, капча и ошибки неверного пароля не регрессируют.

## 6. Фаза 4 — фоновые задачи, демоны и почта

- [ ] Приостановить все автоматические операции FS LMS: cron core и модулей, очистки/истечения, уведомления, снимки рейтинга, AdSync delivery/reconcile, доставку после HTTP-ответа, приём регистрации видео.
- [ ] Сохранить расписания и существующие очереди. Пропуск тика не помечает работу выполненной, не расходует попытку и не переводит её в ошибку.
- [ ] Проверять обслуживание в сервисных точках запуска, чтобы прямой вызов сервиса и shutdown-доставка не обходили паузу. Ручные команды обслуживания должны иметь явно различимый контекст, а не случайно запускать автоматический хвост.
- [ ] Для внешнего uploader возвращать временный 503, сохраняя HMAC и контракт повторов. Проверить фактический backoff: 4xx у uploader считается терминальной ошибкой.
- [ ] Разделить запрет приёма изменений сайтом и фактическую паузу демона. Если демон продолжает скачивать/загружать во внешнее хранилище, обеспечить его паузу поддержанным протоколом или документированной серверной командой; не показывать ложный статус «остановлен».
- [ ] Ввести учёт уже запущенных автоматических операций: при включении запретить новые, завершить текущий безопасный пакет и подтвердить остановку. Статусы: «завершаются операции», «пауза подтверждена», «внешняя пауза не подтверждена». Истёкшая блокировка не должна ошибочно доказывать завершение живого процесса.
- [ ] Обеспечить защиту от гонки между регистрацией новой работы и включением режима. Для внешних/неохваченных процессов явно указать отсутствие гарантии.
- [ ] Остановить отправку почты FS LMS на общей точке и проверить обходы, включая письма WooCommerce от LMS-сценариев. Не выключать чужую почту WordPress глобально без необходимости.
- [ ] Письма от событий во время обслуживания не ставить в отложенную очередь. Уже существующую очередь, если она реально есть, сохранить и приостановить. Не создавать очередь писем ради этой фичи.
- [ ] Пропуск письма отличать от успешной отправки и транспортной ошибки; не провоцировать повторы бизнес-операций из-за `false` от подавленной отправки.
- [ ] Административные изменения аккаунтов могут сохранить необходимые задания AdSync, но не отправлять их до выключения режима. Секреты и письма с паролями не логировать.
- [ ] После выключения возобновить задачи без дубликатов и рассылки подавленных писем. Просроченные попытки/брони обрабатываются по исходным срокам; обслуживание автоматически не продлевает экзамены и дедлайны. Это указать перед включением.

**Образцы:** `CronController`, `RecoveryController`, `AdSyncCronController`, `AdSyncController::flushAfterResponse()`, `VideoRestController::postVideo()`, `EmailService`, `EmailSubscriber`.

**Проверка:** запуск каждого тика в режиме обслуживания не меняет доменные данные и не вызывает внешнюю доставку; после выключения очередь продолжается один раз. Отдельно проверить долгий пакет и конкурентное включение. Без подтверждения паузы не показывать «можно начинать работы».

- [ ] Заблокировать новую оплату через все актуальные пути: создание брони/заказа, checkout, повторную оплату существующего заказа и Store API. Не ограничиваться скрытием кнопки.
- [ ] Для уже начатых платежей разрешить проверенному шлюзу сохранить подтверждение и статус заказа в WooCommerce. Это явное исключение к остановке автоматических записей, необходимое для сохранности оплаты. Существующие проверки подписи и подлинности обязательны.
- [ ] Приостановить LMS-обработку `WooExamController::onOrderChanged()` и автоматические вызовы `ExamPaymentReconciler::reconcileOrder(int $orderId)`; не выдавать доступ, не менять учебные данные и не доставлять outbox во время паузы.
- [ ] После выключения использовать существующую идемпотентную сверку Woo-заказов и минутный тик, восстанавливающий пропущенные события. Учесть оплаченные заказы и истёкшие брони; сверка не должна зависеть только от повторного webhook.
- [ ] Проверить конкретный установленный шлюз и все связанные письма/побочные эффекты WooCommerce: подтверждение оплаты сохраняется, но почта LMS-сценариев не отправляется. Если обнаружится интеграция вне WooCommerce, отдельно доказать сохранность её подтверждений; не возвращать фиктивный успешный приём.
- [ ] Не отключать несвязанные товары/платежи WooCommerce без основания; определить фактическую область интеграции по текущему магазину.

**Проверка:** ранее открытая страница оплаты не создаёт новую оплату через сайт; подтверждение ранее начатого платежа не теряется; повтор webhook/сверки не дублирует доступ. Эта фаза не считается завершённой без проверки используемого шлюза.

- [ ] В описании указать: пользователям доступно чтение; администраторы продолжают изменения; почта и автоматические службы приостановлены; текущие дедлайны не продлеваются; несохранённые действия пользователей не будут приняты.

# Переименование файлов публичных заданий — план реализации

Дата: 2026-11-07. Статус: план, реализация не начата. Независимая фича; план обслуживания выше сохраняется.

## 11. Поведение и область действия

При публикации публичного задания файл получает имя по номеру задания: `123.txt` → `1000.txt`. Номер — сохранённый `post_name`, как в `TaskNumberService`, а не ID записи и не термин номера экзаменационного задания. Расширение и содержимое сохраняются.

- Публичные задания: `PostTypeResolver::isTaskPostType()` (`{subject}_tasks`).
- Приватный банк: `PostTypeResolver::isProblemPostType()`; его записи, вложения и рабочие ссылки не изменяются. `isBankPostType()` для отбора не использовать: включает оба банка.
- Обрабатывать скачиваемые файлы из `file`, `file_primary`, `file_secondary` и `task_materials[attachment_ids]`. Аудио, изображения внутри условия/решения и произвольные ссылки в HTML в область переименования не входят.
- Сохранить существующее правило массовой правки: `file` → `1000.ext`, `file_primary` → `1000-1.ext`, `file_secondary` → `1000-2.ext`. Дополнительные материалы — стабильные свободные порядковые суффиксы; одиночный материал без других файлов → `1000.ext`. Не менять имена всех файлов из-за добавления одного нового материала.
- Черновики, autosave, revisions и неудачная публикация файлы не меняют. Повторная публикация и повторный запуск обработки идемпотентны. Замена файла в уже опубликованном задании также нормализует его имя после сохранения полей.
- Общий файл копируется для публичного задания; оригинал и attachment, используемые приватным банком/другими записями, сохраняются. При необходимости создаётся отдельное вложение, привязываемое только к публичному заданию.
- Внешние URL и неподдерживаемое удалённое хранилище не скачивать и не переименовывать молча: пропуск с объяснением. Поддержку CDN/offload проверять по фактическому хранилищу.
- Физическое имя и ссылка должны соответствовать правилу; одного изменения заголовка attachment или атрибута `download` недостаточно.

# Настройки рейтинга по предметам — план переработки

Дата: 2026-11-07. Статус: план, реализация не начата.

## 17. Поведение и интерфейс

Сначала администратор выбирает предметы, в которых показывается рейтинг. У каждого предмета собственный `fs-toggle` через существующий `render_fs_toggle()`. Поля рейтинга появляются под предметом только после включения его переключателя.

- Вкладка «Рейтинг» начинается со списка предметов. Каждая карточка содержит название предмета и переключатель «Отображать рейтинг».
- При выключенном переключателе видна только шапка карточки; поля скрыты через `hidden` и выключены для браузерной валидации. При включении появляются настройки именно этого предмета: практика, самостоятельная, домашняя работа, опрос, экзамены/контрольные, бонус за посещаемость, длина серии, исключённые ученики.
- Один и тот же предмет имеет общие настройки для всех своих групп. Разные предметы полностью независимы.
- Выключение скрывает рейтинг от учеников, сохраняя коэффициенты, бонусы и исключения для повторного включения. Сотрудники сохраняют доступ к расчёту по существующим правам; это соответствует текущей семантике переключателя видимости.
- Поля показываются сразу при переключении, но серверное состояние меняется только после нажатия «Сохранить». Одна общая кнопка сохраняет изменённые карточки атомарно; рядом статус результата.
- Все существующие предметы при переходе сохраняют текущую видимость и эффективные параметры. Новый предмет после перехода получает выключенный рейтинг и исходные значения полей; включение не копирует настройки случайного соседнего предмета.
- Архивные предметы явно помечены, их сохранённые настройки не теряются. Удаление/смена ключа предмета должно согласованно удалять/переносить его настройки.
