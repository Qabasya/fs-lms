# AD Sync — техническое задание для сервера AdSync в офисе

> Контракт между сайтом (модуль `Inc\Modules\AdSync`) и сервисом **fs-adsync** в офисе
> (репозиторий `Qabasya/AdSync`), который создаёт учётные записи в Active Directory по заявкам.
> Модель — **push**: сайт сам отправляет задание сервису и в том же ответе получает результат.
>
> Документ нормативный для обеих сторон: сеть, TLS, подпись запросов, эндпоинты, коды ответа.
> Копия лежит в репозитории сервиса (`.docs/AdSyncPythonService.md`) — меняются синхронно.

---

## 1. Схема и роль сервиса

```
Сайт (WP, Beget) ──HTTPS POST──▶ белый IP офиса :8443 ──проброс──▶ контейнер AdSync (11.11.11.22)
                                                                    └─LDAPS─▶ контроллер домена
```

- Сервис — HTTP-сервер (FastAPI/uvicorn) в Docker: публичный API для сайта на `:8443` по HTTPS
  и локальный `/health` + `/status` на `:8091` (Docker HEALTHCHECK, наружу не пробрасывается).
  `restart: unless-stopped` + autostart контейнера в Proxmox.
- Сайт сам ставит задания в очередь, сам ретраит и сам копит их, пока офис недоступен. Сервер ничего
  не опрашивает и на сайт не обращается — только отвечает на запросы.
- Пускать на порт только сайт: на роутере правило «разрешить TCP с исходящего IP сайта
  (`87.236.20.5`) → контейнер:8443, остальным — запретить» (см. `Tasks.md`, этап 1).

## 2. TLS

- Сертификат **самоподписанный, с белым IP офиса в SAN**, срок 10 лет:
  ```bash
  openssl req -x509 -newkey rsa:3072 -sha256 -days 3650 -nodes \
    -keyout server.key -out server.crt -subj "/CN=adsync-office" \
    -addext "subjectAltName=IP:92.101.127.156" -addext "basicConstraints=critical,CA:TRUE"
  ```
- Файлы лежат в `config/tls/` сервиса (`TLS_CERT_FILE`, `TLS_KEY_FILE`); без них сервис не
  стартует. `server.key` не покидает контейнер. `server.crt` копируется на хостинг выше `public_html` и
  прописывается на сайте: `define( 'FS_LMS_AD_SERVER_CERT', '/путь/к/adsync-server.crt' );`.
  Сайт доверяет **только** этому сертификату — подменить сервер нельзя даже чужим валидным.
- В контейнере — синхронизация времени (chrony): подпись привязана ко времени.

## 3. Аутентификация запросов

Каждый запрос сайта подписан общим секретом `FS_LMS_AD_HMAC_SECRET` (генерируется кнопкой в
настройках модуля; одно значение в `wp-config.php` сайта и в `.env` сервиса).

| Заголовок | Значение |
|---|---|
| `X-Fs-Timestamp` | unix-время запроса, секунды |
| `X-Fs-Signature` | `hex( hmac_sha256( METHOD + "\n" + PATH + "\n" + TIMESTAMP + "\n" + BODY, secret ) )` |

- `METHOD` — `GET`/`POST` заглавными; `PATH` — путь без хоста и query (`/v1/jobs`); `BODY` — сырое
  тело как пришло (у `GET` — пустая строка).
- Сервер **обязан** отвергнуть запрос кодом `401`, если заголовков нет, `|now − timestamp| > 300`
  или подпись не совпадает (сравнение `hmac.compare_digest`).
- Метод и путь входят в подпись, чтобы подписанное тело нельзя было переиграть на другой эндпоинт.
  Повтор того же задания закрывает `idempotency_key` (§4.1).

Эталон (совпадает с юнит-тестом сайта `AdRequestSignerTest`):
```python
hmac.new(b"topsecret", b'POST\n/v1/jobs\n1700000000\n{"a":1}', hashlib.sha256).hexdigest()
```

## 4. Эндпоинты

### 4.1. `POST /v1/jobs` — одно задание

Тело — по типу события:

| `event` | Поля | Что делать в AD |
|---|---|---|
| `provision` | `id, event, idempotency_key, username, password, first, last, subject_key` | создать учётку сразу в OU направления (по `subject_key`), задать пароль, включить; учётка в «Отчисленных» — реактивировать и перенести в OU направления |
| `deprovision` | `id, event, idempotency_key, username` | отключить и перенести в `OU=Отчисленные` |
| `password` | `id, event, idempotency_key, username, password` | задать пароль (учётку не включать и не переносить) |

Когда сайт присылает задание:

| Событие на сайте | Задание | Условие |
|---|---|---|
| ученик подал заявку | `provision` (`idempotency_key: app:{id}`) | направление отмечено в настройках модуля |
| заявка истекла / удалена в корзину | `deprovision` | по заявке был `provision` |
| ученик отчислен | `deprovision` | у ученика не осталось других действующих зачислений (пробный доступ не считается) |
| ученик **снова зачислен** | `provision` (`reenroll:record:{id}`) — реактивация | последнее задание по учётке — `deprovision`, новое направление отмечено в настройках. Восстановление из архива учётку не трогает: направление выбирается при зачислении |
| администратор сменил пароль | `password` (`password:person:{id}:{время}`) | учётка под управлением сайта и не в «Отчисленных» (при реактивации пароль уйдёт с `provision`) |

Пароль в очереди сайта не хранится: он читается в момент отправки — из заявки или из зашифрованной
копии пароля пользователя. Если копии нет (пароль меняли в обход сайта), задание сразу «мёртвое».

Ответ — **синхронный**, `200` с JSON:

```json
{ "status": "done", "error": null }
{ "status": "failed", "error": "учётная запись вне управляемой зоны" }
```

| Ответ сервиса | Когда | Что делает сайт |
|---|---|---|
| `200` + `status: done` | задание выполнено (в т.ч. повтор уже выполненного) | задание отправлено |
| `200` + `status: failed` | ошибка **задания**: учётка вне управляемой зоны, не подобрать CN, ошибка LDAP-операции | ретрай с бэкоффом 1м → 2м → … ≤ 1 ч, после 6 неудач — «мёртвое» |
| `422` | тело не прошло валидацию (неизвестный `event`, нет поля) | как `failed` |
| `401` | подпись неверна или просрочена | вся доставка на паузу (неверный секрет — вина конфигурации, не задания) |
| `503` | контроллер домена недоступен и после переподключения | вся доставка на паузу 1м → … ≤ 1 ч, попытка **не тратится** |
| нет соединения, таймаут 5 с | офис недоступен | то же, что `503` |

Правила:
- **Незнакомый `subject_key`** — учётка создаётся в `AD_OU_FALLBACK` без группы направления,
  ответ `done` + WARNING в журнале сервиса: ученик должен войти сразу, карту направлений админ
  дополнит потом.
- **Повтор задания** — штатная ситуация (таймаут пришёл раньше ответа, ретрай после `failed`).
  `idempotency_key` — ключ журнала и счётчика «мёртвых», **не кэш ответа**: задание выполняется
  заново, все операции идемпотентны («уже существует», «уже в группе», «уже отключена» — успех).
  Ключи: `app:{id}` (provision), `deprovision:app:{id}`, `deprovision:person:{id}`.
- Задание обрабатывается строго по одному (одно LDAP-соединение) и укладывается в **5 секунд** —
  таймаут сайта.
- **Пароль приходит только в `provision`**, живёт только в памяти на время запроса и нигде не
  пишется — ни в журнал, ни в логи (redaction-фильтр — страховка).
- `subject_key` — слаг направления (`inf_ege`, `inf_oge`, `robo`, `python`), не DN. Карта
  `subject_key → OU + группа` — `subjects.yaml` сервиса.

### 4.2. `POST /v1/reconcile` — сверка (раз в сутки)

```json
{ "usernames": ["i.petrov", "a.ivanova"], "apply": false }
```

`usernames` — все логины, которые **должны** оставаться активными: активно зачисленные ученики и
заявки в живых статусах. Сервис проходит по OU направлений и `AD_OU_FALLBACK` (без «Отчисленных»)
и для активных учёток, которых нет в списке:
- `apply: false` — только пишет в журнал, кого отключил бы (первую неделю);
- `apply: true` — отключает и переносит в `OU=Отчисленные`, как `deprovision`.

Предохранители — нарушение любого отменяет сверку целиком, никто не тронут (и в режиме журнала):
пустой список при непустой зоне; к отключению больше `RECONCILE_MAX_DISABLE` учёток или больше
`RECONCILE_MAX_DISABLE_PCT`% зоны. Учётки моложе `RECONCILE_GRACE_MINUTES` не трогаются. Сверка
односторонняя: никого не включает и не создаёт.

Ответ:
```json
{ "status": "ok", "applied": false, "disabled": ["x.old"], "abort_reason": null }
{ "status": "aborted", "applied": true, "disabled": [], "abort_reason": "к отключению 12 учёток, порог 10" }
```
`disabled` — отключённые (при `apply: false` — кого отключил бы). Сайт показывает число или
причину отмены в настройках модуля. Таймаут — 30 с; недоступный DC — `503`.

Режим переключается в настройках модуля («Сверка: отключать лишние учётки»); вручную —
`wp fs-lms ad reconcile [--apply]`.

### 4.3. `GET /v1/health` — проверка связи

Подписан так же. Сервис делает пробный запрос к DC: `200 { "status": "ok", "ldap": "ok" }`;
DC недоступен — `503`. Используется кнопкой «Проверить соединение» и `wp fs-lms ad health`.

## 5. Операции в AD (ldap3)

- Подключение под сервис-аккаунтом `svc-adsync` с делегированием только на управляемую зону
  (OU направлений, `AD_OU_FALLBACK`, `AD_OU_DISABLED`), по **LDAPS 636** с проверкой сертификата DC.
- **`provision`, учётки нет:** создать **отключённой** (AD не даёт включить учётку без пароля) →
  пароль (`unicodePwd` через `extend.microsoft.modify_password`) → включить (`userAccountControl=512`)
  → членство в группе направления. `sAMAccountName=username`, `userPrincipalName=username@<суффикс>`,
  `cn`/`displayName` из `first` + `last`; тёзки получают разные CN («Имя Фамилия (логин)»).
- **`provision`, учётка есть:** в зоне — обновить пароль, включить, группа; в «Отчисленных» —
  реактивация (включить, перенести в OU направления); **вне зоны — `failed`, объект не трогать**.
- **`password`:** задать пароль учётке в зоне (в т.ч. в «Отчисленных» — она остаётся отключённой).
  Учётки нет — `failed` (цель не достигнута, после 6 попыток администратор увидит «мёртвое»);
  вне зоны — `failed`.
- **`deprovision`:** `userAccountControl=514` + перенос в `AD_OU_DISABLED`. Учётки нет или уже
  отключена — `done`; вне зоны — `failed`.
- Hard-delete запрещён всегда.

## 6. Конфигурация сервиса

`.env` (см. `.env.example` репозитория сервиса), ключевое для связи с сайтом:

| Параметр | Назначение |
|---|---|
| `FS_LMS_AD_HMAC_SECRET` | секрет подписи — то же значение, что в `wp-config.php` сайта |
| `PUBLIC_PORT` | порт публичного API (8443; проброшен на роутере) |
| `TLS_CERT_FILE`, `TLS_KEY_FILE` | `server.crt` / `server.key` (по умолчанию `/app/config/tls/`) |
| `HMAC_MAX_SKEW_SECONDS` | окно подписи по времени (300) |
| `RECONCILE_MAX_DISABLE`, `RECONCILE_MAX_DISABLE_PCT`, `RECONCILE_GRACE_MINUTES` | предохранители сверки |
| `LDAP_*`, `AD_UPN_SUFFIX`, `AD_OU_DISABLED`, `AD_OU_FALLBACK`, `SUBJECTS_FILE` | доступ к AD и карта направлений |
| `AD_PROFILE_PATH_TEMPLATE` | путь к перемещаемому профилю, `{username}` — логин; в `.env` — в одинарных кавычках |
| `AD_PASSWORD_NEVER_EXPIRES` | «Срок действия пароля не ограничен» (`true`); приводится при provision и password |

## 7. Наблюдение

Журнал обработок — `state.db` сервиса (без паролей), логи — файл и Loki (`service="fs-adsync"`,
метки `event`: `job_done`, `job_failed`, `job_dead`, `password_changed`, `reconcile_done`, `reconcile_dry_run`,
`reconcile_aborted`, `ad_unavailable`, `signature_rejected` …). На стороне сайта — счётчики
очереди, последняя доставка и последняя ошибка в настройках модуля.

## 8. Требования к домену (от AD-администратора)

- Парольная политика домена должна принимать простые пароли из формы заявки (сейчас ослаблена:
  мин. длина 3, сложность отключена), иначе `provision` будет возвращать `failed`.
- OU по направлениям и `OU=Отчисленные` созданы заранее, их DN — в `.env`.
- Сервис-аккаунт с правами на эти OU (создание, изменение, перенос, запись `unicodePwd`).
- Права на ресурсы, ярлыки, GPO — по OU направления; к рантайму сервиса не относится.

## 9. Ввод в строй

1. «Проверить соединение» в настройках модуля — зелёное.
2. Тестовая заявка → учётка в нужной OU за секунды → вход на ПК в офисе.
3. Тестовое отчисление → учётка в `OU=Отчисленные`, отключена.
4. Выключить сервер → подать заявку → включить → задание доехало из очереди само
   (или «Отправить сейчас» в настройках).
5. Сверка в режиме «только журнал» неделю → включить отключение.
6. Разобрать старые «мёртвые» задания («Повторить мёртвые» или вручную).
