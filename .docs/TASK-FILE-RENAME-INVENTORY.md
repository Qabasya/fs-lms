# Переименование файлов публичных заданий: инвентарь

Проверено по исходникам 2026-11-07. Это результаты фазы 0 разделов 11–16 `.docs/Tasks.md`; реализация и интеграционные проверки ещё не выполнены.

## Источники и сохранение

| Путь | Фактический порядок и последствия |
|---|---|
| Редактор WordPress | `MetaBoxController::handleMetaSave()` на `save_post`: пропускает autosave, проверяет тип публичного задания **или** приватной задачи и nonce, затем `saveFieldsMerge()`; для связки вызывает `TaskBundleService::syncChildren()`. Нормализацию следует вызывать после сохранения, повторно проверяя фактический статус и публичный тип. Статусный хук срабатывает раньше готовности полей. |
| Inline-редактор | `TaskContentCallbacks::ajaxSaveTaskContent()` сначала обновляет или вставляет пост со статусом `publish`, затем вызывает `saveFields()`. Ответ содержит ID, title, template и edit_url, но не свежую мету. Обработка должна идти после `saveFields()` с проверкой сохранённого статуса и номера; обновление данных открытого редактора требует отдельной проверки JS-контракта. |
| Массовая правка | `TaskBulkEditService::plan()` проверяет конфликты, `apply()` делает снимок, временно освобождает слаги, выполняет файловую партию, записывает мету и итоговые слаги; при ошибке восстанавливает снимок. Сохранить обмен путями и откат; обработка на обычных хуках не должна сработать внутри партии. |
| Создание и легаси-импорт | `TaskManager::createNewTask()` создаёт draft с номером `TaskNumberService`, потом добавляет термы и мету; `LegacyTaskImportService` также создаёт черновик и позднее пишет мету. Черновики не нормализуются. |
| Отложенная публикация | Отдельной нормализации в существующем коде не найдено. Нужна проверка перехода в `publish` для уже сохранённой меты, с исключением редакторских/импортных промежуточных состояний. Порядок реального WP-cron следует покрыть интеграционным тестом. |
| Перенос предмета | `SubjectBundleImportService::import()` сначала импортирует медиа, затем `importSections()` восстанавливает записи по порядку после remap ID и URL; `PostRestorer` записывает запись и мету раздельно. При ошибке работает журнал `ImportedEntitiesCollector` и откат. Нормализация не должна изменять общие медиа посреди импорта; её завершение и откат нужно согласовать с журналом. |
| Составное задание | `MetaBoxController` синхронизирует детей после сохранения родителя; `TaskBundleService` отдельно пишет мету детей и распространяет статусы. Порядок нормализации относительно синхронизации требует теста, чтобы не копировать устаревшие ссылки. |

`PostTypeResolver::isTaskPostType()` выбирает CPT с суффиксом `_tasks`; приватный `fs_lms_problems` определяется отдельно через `isProblemPostType()`. `isBankPostType()` шире обоих банков: включает также курсы, статьи и другие типы.

## Данные и потребители

* `LinkField` сохраняет прямые строки URL в `PostMetaName::Meta`: `file`, `file_primary`, `file_secondary`. `TaskMetaService::getTaskFiles()` выводит имя из URL и максимум два файла; `fileLink()` для своего origin отдаёт путь с query. Нужны проверки кодирования и относительных URL: текущий `TaskBulkFileService::urlToPath()` принимает только URL с базовым uploads URL, игнорируя различие http/https.
* `FileAttachmentsField` хранит массив `task_materials[attachment_ids]`. `TaskMetaService::getTaskMaterials()` получает URL по ID и строит имя скачивания из заголовка attachment плюс расширение. `AttemptTaskViewBuilder` тоже получает материал по ID, но использует заголовок как имя. Нельзя глобально менять существующий общий attachment; отдельная копия требует отдельного attachment с корректным заголовком.
* `MediaCollector` ищет ссылки не только по ID, но и в произвольных строках и HTML, а также `wp-image-{id}`; статьи дополнительно используют атрибуты шорткодов. `RefRemapper` отдельно обрабатывает `attachment_ids`. Приватные задачи, статьи, уроки и внешние потребители могут ссылаться на те же файлы. `ExamVariantGuard` проверяет ссылки на attachment в мете замороженных заданий; `AttemptTaskViewBuilder` читает актуальную мету задания. Существование всех возможных снимков и внешних ссылок по одному поиску не доказывается.
* `TaskBulkFileService::isShared()` ищет фрагмент относительного пути только в сериализованной `PostMetaName::Meta` других записей. Это шире трёх полей публичных заданий, но не охватывает attachment ID без URL, другую мету, контент, опции, внешние системы и снимки. Отсутствие совпадения и `post_parent` не доказывают эксклюзивное владение. Исходный файл сохранять как копию даже при отсутствии найденных ссылок; автоматически не удалять.

## Текущий файловый механизм и ограничения

* `TaskBulkFileService::plan()` обрабатывает только три прямых поля, пропускает внешние URL без предупреждения, предупреждает об отсутствующем локальном файле и attachment с миниатюрами. Суффиксы: пустой, `-1`, `-2`. При совпадении basename сразу пропускает файл, до проверки существования и происхождения.
* `execute()` копирует общие файлы, затем переносит остальные через временные имена; для перемещённого attachment вызывает `update_attached_file()`. Проверки коллизии внутри него нет: `TaskBulkEditService::resolveConflicts()` проверяет цели отдельно, разрешая освобождение файла другой операцией move. Прямой вызов `execute()` без проверки опасен; проверка и запись должны быть защищены от гонки и перезаписи.
* `urlToPath()` проверяет строковый префикс uploads и `..` до `rawurldecode()`, но не проверяет канонический путь/символические ссылки. Для нового контракта проверять декодированный путь и `realpath` относительно разрешённого uploads, включая родительский каталог цели; пути вне него и symlink наружу запрещены. Также проверить отсутствующее расширение и корректность номера.
* Локальный uploads с доступным оригиналом может обрабатываться только после проверок пути и файла. CDN URL с локальным оригиналом поддерживать лишь при достоверном сопоставлении attachment/хранилища с локальным путём; иначе явно пропускать. Offload без локального оригинала и внешние URL не скачивать, выдавать причину. Фактическая конфигурация CDN/offload на развёртывании в этом исследовании не проверена.
* Целевой файл может быть занят другим предметом, старым заданием или сторонним файлом. Содержимое и размер не подтверждают владение. При конфликте нужен отдельный стабильный каталог, привязанный к предмету и ID, с точным именем файла и защитой одновременной записи. Разрешение каталога и проверка прав требуют интеграционного теста.
* Сохранение старого пути обязательно: ранее опубликованные прямые URL, материалы, снимки и сторонние ссылки должны продолжать работать. Переключать только мету текущего задания после подготовки копии; сохранять исходный attachment для других пользователей. Файловая система и БД не образуют общей транзакции: нужны журнал, восстановление и тест сбоя на каждом этапе.

## Проверки до приёмки

1. Поведенческие тесты: оба редактора после сохранения полей, повторная публикация, замена файла, отложенная публикация, draft/autosave/revision и приватный банк; отдельно составная задача и завершение bundle-импорта.
2. Файлы: ID и URL одного исходника, общий с приватным банком и HTML статьи, два поля, несколько материалов, повторный запуск, конфликт разных предметов, путь вне uploads, закодированный traversal, symlink, отсутствие локального файла, CDN и offload.
3. Проверить сохранность байтов, старой и новой ссылок, имени скачивания, attachment, откат при сбое и конкурентные запуски; подтвердить отсутствие изменений в dry-run. Прогнать регрессии `TaskBulkFileServiceTest` и `TaskBulkEditServiceTest`.
