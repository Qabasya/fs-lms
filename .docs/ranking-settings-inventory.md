# Настройки рейтинга: инвентарь перед переработкой

## Реализация

Настройки находятся в конфигурации плагина в `ranking_subjects` и редактируются карточками предметов. Включение управляет видимостью для учеников; расчёт для сотрудников остаётся доступным по их правам. Все группы одного предмета используют общие коэффициенты и список исключений. Изменение настройки начинает новое сравнение мест для затронутого предмета; прочие предметы сохраняют динамику.

При первом запуске миграция переносит действующие общие настройки во все существующие предметы, включая архивные. Новые предметы получают выключенный рейтинг и стандартные коэффициенты. Изменения конфигурации и жизненного цикла предметов сериализуются блокировкой базы; перед созданием предмета с повторно используемым ключом его прежняя политика сбрасывается. Поколение предмета участвует в проверке снимка и не позволяет использовать динамику удалённого предмета. Технический ключ штатными средствами не переименовывается; при добавлении такой операции потребуется явно переносить его настройки.

Проверено по исходникам 2026-11-07; документ описывает существующие контракты и предлагаемые границы новой схемы.

## Текущие данные и потребители

- `PluginConfigRepository::get()` объединяет опцию `PluginConfig` с `DEFAULTS`, `save()` сохраняет только разрешённые ключи и поверх всей текущей опции. Глобальные `ranking_*`: practice 0, independent/homework/survey/assessment 1, attendance_bonus 0, attendance_streak_length 3, hidden_subjects и excluded_students — пустые массивы. `PluginConfig::rankingSettings()` нормализует эффективные значения; переход должен брать именно их, сохраняя дробные веса.
- `RankingSettingsCallbacks::ajaxSaveRankingSettings()` проверяет `Nonce::Config` и `ManageLmsPlatform`. `RankingSettingsService::save()` проверяет весь плоский патч до записи: целые веса 0–1000, длина 2–100, списки в виде CSV; при любом изменении вызывает `RankingSnapshotRepository::clear()`.
- `PluginConfig::viewState()['ranking']` питает общий шаблон; `RankingSettingsViewService::build()` возвращает все предметы, всех учеников и ранее исключённых через `PersonRepository::findByIsStudent(true)`/`findByIds()`. Шаблон `settings-ranking.php` и `src/js/admin/services/settings/ranking-settings.js` сейчас работают с общей формой и глобальными идентификаторами.
- `RankingPointsPolicy` читает глобальные веса и исключения; `RankingCalculationService::scoresForSubject()` уже принимает ключ предмета, получает один набор весов и отдельно исключения, и применяет их к работам, экзаменам и посещаемости. Текущие и прошедшие периоды пересчитываются по действующей политике, исторических копий коэффициентов нет.
- `SubjectRankingService` использует этот расчёт для сотрудников и учеников, повторно ранжирует группу и отдаёт разбивку сотрудникам. `LearnerRankingSection` использует тот же расчёт для плиток. `RankingAccessService` проверяет `isLearnerRankingVisible()` при построении доступных ученику направлений; `LearnerRankingSection` проверяет её отдельно. Сотруднический доступ определяется правами, а не видимостью для ученика. `src/js/profile/ranking.js` отображает полученную сервером разбивку и не вычисляет веса.
- Фоновый `CronController` запускает `RankingSnapshotService::capture()` раз в 15 минут; снимок строится для `readActive()`, затем `trend()` читает места по предмету/группе/ученику. Опция снимка содержит `interval`, `boundary`, `captured_at`, `season`, `subjects`. У репозитория есть только `read`, `save`, `clear`.
- Релевантные тесты: `RankingSettingsServiceTest`, `RankingSettingsCallbacksTest`, `SubjectRankingServiceTest`, `LearnerRankingSectionTest`, `RankingSnapshotServiceTest`, `RankingSnapshotBuilderTest`, `RankingSnapshotTransactionTest`, `RankingSnapshotPeriodTest`, `tests/js/ranking-settings.test.mjs`.

## Жизненный цикл и ученики

- `SubjectRepository::readAll()` включает архивные DTO, `readActive()` исключает их, `getByKey()` проверяет существование. Архивация меняет только флаг; настройки должны сохраняться. Создание через `SubjectCrudCallbacks::ajaxStoreSubject()` отклоняет занятый ключ. `ajaxUpdateSubject()` меняет название, сохраняя ключ: штатного переименования технического ключа здесь нет.
- Удаление идёт через `DeleteSubjectEvent` → `SubjectDeletionCascadeHandler`, где удаляется запись предмета. `ImportRollbackService` также напрямую вызывает `SubjectRepository::remove()`. При реализации очистки нужно учесть оба пути и повторное создание того же ключа. Отдельной операции переноса ключа в проверенном CRUD нет; если она появится, перенос конфигурации станет её явной обязанностью.
- `LearnerRankingRepository::studentIds($subject)` и `roster($subject)` выбирают активные записи зачисления групп данного предмета; исключены общие, самостоятельные и открытые группы. `roster()` содержит ID, имена и группы; его можно использовать как источник выбора учеников предмета, дополнив ранее выбранных через `PersonRepository::findByIds()`, чтобы не потерять выбывших. Не выдавать в настройки дополнительные персональные данные.

## Границы новой схемы и перехода

- Внутри `PluginConfig` предлагается версия схемы и карта `ключ предмета → {enabled, practice, independent, homework, survey, assessment, attendance_bonus, attendance_streak_length, excluded_students}`; оба верхнеуровневых ключа должны входить в `DEFAULTS`. До завершения перехода чтение использует прежние эффективные параметры; после перехода отсутствие записи означает выключенный рейтинг с исходными значениями, без наследования глобальной политики. Неизвестный ключ недопустим в сохранении и скрыт от ученика.
- Однократный переход заполняет все существующие предметы, включая архивные, эффективными глобальными параметрами и исключениями; `enabled` выводится из прежнего списка скрытых. Переход не перезаписывает уже существующие предметные записи и завершает версию только после успешной записи. Новые предметы получают выключенное состояние. Патч валидируется целиком, мержится по предмету и сохраняет чужие поля и соседей. Существующие дробные значения нельзя округлять или принуждать к повторной валидации при одном переключении видимости.
- `RankingSnapshotTransaction::read()` обеспечивает согласованный read-only срез MariaDB, но **не является блокировкой обновления настроек или сохранения снимка**: запись снимка происходит после завершения транзакции. Поэтому очистка снимка при сохранении может быть перезаписана одновременно завершившимся старым capture. Нужна предметная проверка версии/fingerprint политики при чтении тренда и согласованное обновление снимка; простого удаления одной ветки недостаточно. Параллельные read-modify-write полной опции настроек также требуют согласованного протокола, чтобы не потерять изменения соседних предметов.
- Механизм data-миграций регистрируется в `Init` через `MigrationRunner`; перед реализацией следует выполнить инструкции `.agents/skills/db-migrations/SKILL.md` и проверить порядок запуска/повторного применения.
